# Каталог: сохранение, очередь и интерфейс

Модуль `modules/catalog` сохраняет нормализованные карточки Ozon в отдельную
PostgreSQL новой панели. Он использует `integrations.public`, не обращается к
Seller API напрямую и не читает ключи. Данные старой панели не переносятся.

## Что работает

- Раздел «Товары»: кабинет, состояние, поиск по названию/артикулу, точному SKU,
  ID Ozon или штрихкоду; 30 карточек на страницу. Коды остаются строками с ведущими нулями.
- «Обновить товары»: команда администратора/владельца с CSRF создаёт сохранённое
  задание `catalog.sync`. При выбранном кабинете обновляется он; иначе — активные Ozon.
- Рабочий процесс `python -m pack_v2 --env-file .env.v2 worker` выполняет очередь.
  Он также планирует загрузки активных кабинетов каждые 15 минут. Настройка
  `PACK_V2_CATALOG_SYNC_MINUTES` задаёт интервал, `0` оставляет только ручной запуск.
- Интерфейс показывает очередь, загрузку, число обработанных страниц/карточек,
  ожидание повтора, ошибку и время последнего **полностью успешного** прохода.
  Состояние обновляется запросами к локальной БД. Завершение предлагает показать
  обновлённый список, не сбрасывая введённый пользователем текст автоматической перезагрузкой.

Для обновления установленной v2 выполните миграции и перезапустите **оба**
процесса v2: веб и worker. Новая ревизия схемы — `0003_catalog`, версия — `2.0.0a4`.
Без worker кнопка оставляет задание в очереди. GET страницы/поиск не запускают HTTP
к Ozon. Проверка доступа в кабинетах остаётся отдельной короткой операцией.

## Данные и границы

`Offer` — карточка конкретного кабинета; `Product` — собственная основная карточка.
Новый импорт не создаёт автоматических объединений по артикулу/GTIN, не заменяет
основные карточки и не изменяет их штрихкоды. Существующее сопоставление
`Offer.product_id` сохраняется.

Идентичность загруженной карточки — `(account_id, product_id Ozon)` в `OfferRef`.
Внутренний UUID сохраняется при повторной загрузке. SKU и артикул не подменяют
ID карточки. SKU накапливаются как идентификационные ссылки, в том числе для
будущего сопоставления исторических заказов; изменившийся текущий артикул заменяется.
Противоречащие ссылки разных карточек прерывают страницу, а не объединяют товары.
Одинаковый GTIN у разных карточек/кабинетов допустим и не создаёт объединение.

Наблюдавшийся список штрихкодов заменяет только коды с происхождением `ozon`.
Ручные коды, включая код с тем же значением, сохраняются. Не пришедшие поля не
очищаются: отсутствие имени, штрихкодов или признака архива не означает пустое
значение. Для новой карточки неизвестный архив хранится как `NULL`, а не «активен».
Если имя не пришло, новая карточка получает отображаемое название «Товар Ozon ID».
Версия карточки растёт при изменении содержимого, не из-за каждого чтения времени.

После успешного полного прохода ранее загруженная, но не встреченная карточка
получает `source_present=False` и подпись «Нет в последней загрузке». Это не
удаление, не статус архива и не разрешение освободить Честный знак. Коды, ссылки
и сопоставления остаются. После частичной загрузки такой вывод не делается.

Данные по странице сохраняются одним пакетом с предварительной загрузкой ссылок
и кодов. Вывод страницы использует ограниченный набор запросов, без запроса на
каждую карточку. Добавлены индексы сортировки, ссылок, кодов и истории загрузок.
Все бизнес-таблицы находятся в схеме `pack_v2`.

## Конкуренция, сбои и повторы

- Запрос и автоматический планировщик блокируют кабинет и создают run + задание
  атомарно. Два нажатия или два процесса не создают параллельные загрузки кабинета.
- Каждая запись блокирует кабинет, проверяет его активность/ревизию ключей,
  текущую аренду задания и активность run в одной транзакции. Во время HTTP
  транзакция закрыта. Смена ключа или отключение кабинета останавливают старую загрузку.
- Worker продлевает аренду во время длительного чтения. Истёкший токен не может
  записывать результат или завершать задание, перехваченное другим исполнителем.
- При повторе проход начинается заново. Записи обновляются по прежним ID без дублей;
  счётчики run относятся к текущей попытке. Уже сохранённые порции остаются доступными.
- Успешное завершение run, отметки отсутствия и завершение задания коммитятся вместе.
  Сбой в завершающей транзакции не объявляет частичный каталог полным.
- Временные ошибки повторяются с задержкой и ограничением числа попыток. `Retry-After`
  не сокращается: время следующей попытки сохраняется и учитывается планировщиком.
  401/403, неверная структура и конфликты идентификаторов не запускают бесконечные повторы.
- После последней потерянной аренды интерфейс показывает прерванную загрузку; новый
  ручной запуск восстанавливает работу. Старая попытка не помечается успешной.

Сохранённые задания и аудит содержат UUID, счётчики и безопасные сообщения.
API-ключи и исходные тела ошибок Ozon в них не записываются. Обработчик неожиданной
ошибки журналирует тип исключения и UUID задания, без исходного текста с данными API.

## API

`GET /api/v2/products?account_id=UUID&q=04660291070982&state=all&page=1` — только БД.
Параметры необязательны; состояния: `all`, `active`, `archived`, `missing`.
Доступ требует разрешения на раздел «Товары».

`POST /api/v2/catalog/sync` с JSON `{}` или `{"account_id":"UUID"}` и заголовком
`X-CSRF-Token` возвращает HTTP 202 и `run_ids`. Ответ не означает завершение загрузки.
Повтор активной команды возвращает прежний run. Чтение состояния —
`GET /api/v2/catalog/sync`, доступное товарам либо настройкам.

## Проверки и следующий этап

Тесты используют реальную PostgreSQL 17 и синтетический Seller API. Проверены
повторы, разделение кабинетов, неполные страницы, ведущие нули, права/CSRF,
смена ключей при чтении, утрата аренды и атомарность завершения. Browser smoke
с `--check-catalog` требует отдельный тестовый сервер с MockTransport и worker.
Рабочие ключи и реальные заказы для проверок не используются.

Поверх этих данных подключён [модуль заказов](orders-sync.md). Общая механика
загрузок вынесена в `integrations.public.AccountSync`. Следующий шаг — перенос
сборки, ЧЗ/ГТД и печати; этот модуль их не запускает.
