# Сборка: проверка товаров

Этап `2.0.0a6`, миграция `0005_assembly`. Работает в отдельном приложении `v2/`
для сохранённых FBS-отправлений Ozon в состояниях «Ожидает сборки» и
«Ожидает отгрузки». Исходное приложение и его база не подключаются.

## Сценарий сборщика

1. Открыть «Сборка». Очередь показывает первые 50 доступных отправлений,
   отсортированных по сроку отгрузки. Есть фильтр кабинета; он действует и на
   сканирование в главном поле. Остальные отправления доступны по их коду.
2. Отсканировать стикер, включая `ii…`, номер отправления или штрихкод товара.
   Можно открыть конкретное отправление кнопкой в очереди. При поиске по товару
   выбирается ближайшее доступное отправление, которое ещё не проверено и не занято
   другим сборщиком. При совпадении стикера в нескольких кабинетах нужно выбрать
   кабинет. Точный подтверждённый номер имеет приоритет перед дополнительными кодами.
3. Окно сразу показывает загрузку. В той же транзакции с открытием записывается
   задание точечного `POST /v3/posting/fbs/get`. Его выполняет отдельный worker
   вне транзакции БД. Пока свежий ответ не сохранён, сканы не принимаются.
4. После сверки сканировать каждую физическую единицу. Если окно открыто сканом
   товара, этот первый скан учитывается один раз после успешной сверки. Скан
   стикера открывает окно без увеличения количества товаров.
5. После всех единиц нажать «Сохранить проверку». Результат — **«Товары проверены»**.
   Прогресс восстанавливается при перезагрузке страницы.

Это локальная проверка состава. Она **не переводит отправление в готовность на
площадке**, не создаёт стикер и не означает, что переданы Честный знак или ГТД.
У отправления сохраняются исходный статус и незавершённая проверка требований.
Отдельные интеграционные операции подключаются следующим этапом. При наличии
подсказки о маркировке буква «М» серая: скан товара не является приёмом маркировки
площадкой. Код DataMatrix на этом шаге отклоняется без сохранения полного кода.

## Границы модулей и данные

- `catalog.public` возвращает актуальные штрихкоды карточки площадки и явно
  сопоставленной основной карточки, включая коды других сопоставленных карточек.
  Новых автоматических сопоставлений по одинаковому штрихкоду не создаётся.
- `orders.public` предоставляет состав, очередь, точечную сверку и планирование
  физических единиц. `ShipmentItem` остаётся снимком состава конкретного отправления.
  Для проверки создаются `OrderLine`, `OrderUnit`, `ShipmentUnit`; при повторном
  открытии их ID сохраняются. Грузоместа `Package` здесь не создаются.
- `OrderLine.quantity_source='allocated'` обозначает накопленное количество
  запланированных физических единиц, а не подтверждённое количество заказа
  покупателя. Финансовые данные остаются в снимках отправлений; неизвестная общая
  цена не вычисляется из разных отправлений.
- `assembly` владеет сессиями, снимками строк, фактами сканов, подтверждением
  проверки товаров и журналом команд. Внешние модули вызываются через публичные
  интерфейсы, с общей короткой транзакцией PostgreSQL.
- Последняя проверенная физическая единица сохраняется как `last_unit_id`.
  Это опорная связь для последующего приёма кода маркировки конкретного товара;
  сам приём и передача маркировки пока не подключены.

Точечные загрузки используют `OrderSync.mode='point'` и общий обработчик
`orders.sync`. Они не подменяют состояние общей загрузки заказов и её расписание.
Их журнал содержит ID отправления, ID задания и ревизию ключей; ключи и тела
запросов площадки в очередь не записываются. Запоздалый точечный ответ,
полученный до изменения ревизии отправления, отклоняется и повторяется как чтение.

## Целостность и восстановление

Одновременно у сотрудника одна активная сессия, у отправления один сборщик.
Это проверяют частичные уникальные индексы PostgreSQL и транзакционные блокировки.
Сессия имеет аренду на 180 секунд и случайный токен. Видимая вкладка продлевает
аренду раз в 20 секунд; GET ничего не захватывает и не продлевает. После истечения
аренды тот же сотрудник может продолжить прежние сканы с новым токеном после
повторной сверки. Другой сотрудник начинает новую проверку; ID физических единиц
не меняются. Старые запросы отвергаются.

Каждая команда имеет UUID и HMAC её содержимого, связанный с сотрудником.
Повтор того же запроса возвращает сохранённый результат и актуальный прогресс;
повтор UUID с другим содержимым — конфликт. Успешная команда и скан фиксируются
атомарно. Конкурирующие запросы с одной ревизией не засчитывают две единицы.
Одинаковый штрихкод двух единиц одной позиции допустим; совпадение кода у разных
незавершённых позиций требует уникального штрихкода и не выбирает товар случайно.

Браузер ставит быстрые сканы в последовательную очередь. При потере ответа
повторяется прежний UUID. `sessionStorage` содержит только метаданные команды,
без сканированного кода. После перезагрузки браузер сначала получает результат по
UUID; если команда не завершена, просит повторить последний скан. Несохранённая
очередь быстрых сканов живёт только в памяти вкладки: после её закрытия нужно
досканировать единицы по сохранённым счётчикам.

Полные неизвестные коды, в том числе случайно отсканированный Честный знак,
не сохраняются в журнале команд или аудите. Первый известный код товара хранится
зашифрованным до активации и затем удаляется. Аудит скана содержит ID физической
единицы и ревизию состава. У интерфейса и API нет выдачи чужой сессии или команды.
Все изменения требуют разрешения «Сборка» и CSRF; доступ к товарам/заказам для
самого сканирования не требуется.

Смена ключей, отключение кабинета, потеря подтверждения отправления, отмена,
доставка или изменение состава останавливают старую сессию. Переход между
«Ожидает сборки» и «Ожидает отгрузки» при прежнем составе, изменение цены/названия
и актуализация штрихкодов не сбрасывают проверенные единицы. HTTP 404 при точечной
сверке означает необходимость проверки, а не выдуманную отмену.

Отмена локальной проверки сохраняет её историю и физические назначения.
Она не отменяет заказ на площадке, не освобождает коды маркировки и не переносит
товары в другие отправления. Сохранённую проверку можно сбросить её отменой
в собственном окне; следующий запуск использует прежние физические единицы.

## Ограничения этапа

Комплекты с явно заданными компонентами, несопоставленные позиции и товары без
штрихкодов блокируют активацию без частичного создания физических единиц.
Уменьшение количества, удаление или перенос уже распределённых единиц при
разделении требуют отдельной сверки распределения. Существующие единицы и
маркировки при таком изменении автоматически не освобождаются. Этот этап ещё
не реализует редактор разделения и восстановление распределения после него.
За один запуск допускается до 1000 единиц.

Следующий этап: получение полных требований к экземплярам, ввод ГТД,
сканирование и привязка Честного знака, отдельное подтверждение приёма площадкой.
После этого — сборка/разделение на площадке, сверка фактической готовности,
документы и печать.

## API

Все пути ниже начинаются с `/api/v2/assembly` и требуют входа и разрешения «Сборка».

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/current` | Собственная активная сессия |
| GET | `/{id}` | Прогресс своей сессии |
| GET | `/commands/{command_id}` | Результат команды после потери ответа |
| POST | `/open` | `command_id`, один из `code`/`shipment_id`, необязательный `account_id` |
| POST | `/{id}/activate` | Перейти к сканам после успешной сверки |
| POST | `/{id}/scan` | Учесть одну единицу: `code` |
| POST | `/{id}/verify` | Сохранить проверку товаров |
| POST | `/{id}/retry` | Повторить сверку |
| POST | `/{id}/cancel` | Отменить локальную проверку |
| POST | `/{id}/heartbeat` | Продлить свою текущую аренду |

Команды сессии передают `command_id`, `lease_token`, `revision`; heartbeat —
только `lease_token`. Ответ содержит актуальную сессию. Ожидание чтения — HTTP 202,
конфликт/отклонённый скан — 409, успех — 200. Полное тело кода в ошибке не возвращается.

Миграция добавляет таблицы сборки, ограничения принадлежности к заказу/отправлению,
физическую ревизию и точечные загрузки. При откате до `0004_orders` таблицы сборки
удаляются, точечные задания останавливаются, их ссылки очищаются. Заказы, товары,
физические единицы и назначения сохраняются; таблицы старой панели не затрагиваются.

Проверки: `tests/test_assembly.py`, общая PostgreSQL-серия и опциональный
`tests/browser_smoke.py --check-assembly` на отдельной БД с mock Ozon и worker.
Браузер проверяет загрузку, сохранение после перезагрузки, потерю ответа после
фиксации скана, последовательность быстрых сканов и мобильную ширину.
