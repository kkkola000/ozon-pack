# Оригинальные стикеры Ozon при сборке

Версия `2.0.0a11`, миграция `0010_labels`. Этап реализует получение PDF
в сборке. Архив «Стикеры», срок хранения 6 месяцев и управление печатью —
следующие этапы; исходная панель и её файлы не используются и не меняются.

## Сценарий

После успешной сверки отправления при открытии окна сборки:

- Для «Ожидает отгрузки» ставится задание получения стикера.
- Для «Ожидает сборки» показывается «Стикер будет получен после подтверждения
  готовности Ozon». Передача ЧЗ/ГТД и проверка товаров продолжаются как раньше.
- Когда операция готовности подтверждает состояние Ozon, загрузка ставится
  в очередь в той же транзакции, которая сохраняет результат готовности.
- При разделении используются только подтверждённые дочерние отправления.
  У каждого свой PDF; прежний стикер исходного состава становится неактуальным.
  Случай сохранения номера исходного отправления у одного ребёнка также учтён.

Worker получает оригинал, проверяет его и сохраняет в отдельной PostgreSQL v2
в зашифрованном виде. В окне появляются **«Открыть PDF»** и **«Скачать стикер»**.
Для нескольких отправлений есть **«Скачать стикеры»** и отдельные ссылки PDF.
Ошибки получения показываются отдельно; они не меняют результаты ЧЗ/ГТД,
счётчики товаров и подтверждённую готовность заказа. После исправления прав ключа
или доступности Ozon кнопка **«Повторить загрузку»** повторяет только получение PDF.

Браузер автоматически скачивает готовый файл в свою папку загрузок. Двоичные
данные и токены ссылки Ozon не сохраняются в браузерном хранилище: там только
отметка о скачивании для текущей вкладки/пользователя/поколения документа.
Опрос и перезагрузка открытой сборки не вызывают повторного скачивания.
Если браузер блокирует автоматические/множественные загрузки, остаётся ручная
кнопка. Выбор папки на компьютере и настройки принтеров в этот этап не входят.
Сохранение файла не считается печатью или подтверждением наклеивания стикера.

## Получение из Ozon

| Метод | Назначение |
| --- | --- |
| `/v3/posting/fbs/get` | Проверка состава, номера, актуальных штрихкодов и рабочего состояния до получения PDF и после скачивания |
| `/v3/posting/fbs/package-label/create` | Создание задания ровно для одного отправления |
| `/v2/posting/fbs/package-label/get` | Опрос сохранённого `task_id` без ожидания в веб-запросе |
| `GET file_url` | Потоковое скачивание оригинального PDF по разрешённому адресу Ozon |

ID задания сохраняется до следующего опроса. Перезапуск worker не создаёт
новое задание, если ID известен. Потерянный ответ на создание задания допускает
ограниченную повторную генерацию: это получение документа, не операция `ship`
и не изменение ЧЗ/ГТД. Локальный оригинал остаётся один на отправление/формат.

Поддержаны `small_label` и `big_label`. По умолчанию используется маленький
стикер, параметр `.env.v2` — `PACK_V2_OZON_LABEL_SIZE=small` или `big`.
Размер выбирается по точному `task_type`; неизвестный/отсутствующий размер
не подменяется другим. Переход на другую бумагу в будущем относится к печати.

Незавершённое задание переносится на следующую попытку worker через очередь,
без цикла ожидания внутри HTTP-запроса. Опрос ограничен числом попыток и временем;
`Retry-After` учитывается. `file_url` при промежуточном/неизвестном статусе,
неполный ответ, `unprinted_postings`, HTML вместо PDF, повреждённый или слишком
большой файл не дают состояния «Стикер получен».

## Данные и границы

- `orders.label_target` определяет идентичность документа по отправлению,
  текущим идентификаторам товаров, количеству, кодам стикера и числу грузомест.
  Совпавшие `scanit`/верхний/нижний ШК считаются одной ссылкой, не тремя стикерами.
- `integrations.ozon.documents` знает методы Ozon, задания, допустимые адреса
  и ограничение скачивания. Общий клиент чтения по-прежнему не получает
  разрешения на произвольные записи в API.
- `documents` владеет `shipment_labels`: один текущий оригинал на отправление
  и формат, контрольная сумма, состояние, зашифрованный файл и задание.
  При изменении состава файл заменяется; версии PDF не накапливаются.
- `assembly` вызывает публичный порт получения, а веб-интерфейс читает его
  состояние. `printing` пока не подключён; получение PDF не выполняет печать.

HTTP выполняется без открытой транзакции БД. Каждый результат проверяет
ключи кабинета, токен аренды задания и актуальный состав. Изменение состава,
штрихкодов, отключение кабинета и смена ключей не позволяют выдать старый файл.
Доступ к PDF требует входа и права на сборку; повтор загрузки требует CSRF,
владения сессией и актуальной ревизии. GET PDF не обращается к площадке и
не создаёт задания. Ссылки содержат UUID и поколение; старый URL после замены
файла возвращает конфликт, а не новую наклейку под прежним адресом.

Ключи Seller API передаются только на `api-seller.ozon.ru`. Другие разрешённые
хосты `ozon.ru`/`ozone.ru` получают запрос без ключей кабинета. Каждый редирект
проверяется заново; произвольные домены, HTTP, нестандартные порты и адреса
с логином/паролем отклоняются. Подписанная ссылка площадки не выходит в UI,
журнал или очередь. Максимальный размер PDF — 8 МиБ, документ проверяется
парсером до сохранения. В браузер отдаётся тот же оригинал с `no-store`.

## Проверка и обновление

Тесты используют отдельную PostgreSQL `*_test` и имитацию HTTP Ozon. Проверяются
отложенная готовность, обе схемы разделения, восстановление заданий, смена
состава/ключей во время HTTP, права, повторные команды и ошибки/редиректы PDF.
Тесты Chromium проверяют реальное скачивание, отсутствие дублирования при
перезагрузке, ручное скачивание и сборку с ЧЗ/ГТД после получения стикера.
Живой кабинет и физические принтеры этими тестами не проверяются.

Для обновления остановите только web/worker v2, установите `requirements.lock`
и пакет v2, примените миграции и запустите оба процесса. Ключ шифрования
из существующего `.env.v2` сохраняется. Команды — в [README](../README.md).
