# Честный знак и ГТД: Ozon

Основа этапа: `2.0.0a7`, миграция `0006_instances`. Это следующий этап отдельной панели
`v2/`: получение требований, привязка данных к физической единице и подтверждение
приёма Ozon. В `2.0.0a8` подключена отдельная [операция готовности](ozon-readiness.md).
В `2.0.0a9` добавлено разделение, в `2.0.0a10` — перенос исправлений ЧЗ/ГТД
из основной панели, политика 2 и миграция `0009_marking`. В `2.0.0a11` подключено
[получение оригиналов стикеров](ozon-labels.md). Архив и печать — следующие этапы.
[Яндекс Маркет](yandex.md) подключён отдельной стратегией передачи и подтверждения. Avito пока не подключён.

## Работа сборщика

1. Открыть отправление по ШК товара, стикеру или кнопке в очереди. Сначала worker
   сверяет отправление, затем получает экземпляры и свежие требования. Окно
   показывает загрузку; до завершения сверки сканы не засчитываются.
2. Отсканировать товар. Создаётся факт проверки конкретной `OrderUnit`, а не
   общий счётчик SKU. Если нужен Честный знак, следующее сканирование относится
   именно к этой единице. Другой товар до этого сканировать нельзя.
3. Отсканировать полный Честный знак. Код сохраняется за этой единицей и
   отправлением. Для двух одинаковых товаров нужны два физических скана и два
   разных ЧЗ. На следующую единицу прежний код повторно не засчитывается.
4. Если нужна ГТД, под товаром появляется поле **«Указать ГТД»**. Оно доступно
   после скана единицы. Значение сохраняется по Enter или завершению редактирования.
   При количестве больше одного поле есть у каждой единицы; общая ГТД на весь SKU
   не подставляется без ввода. Уже полученные значения показываются в своих полях.
   Для каждой единицы есть галочка **«Не указывать»**. Пустое поле без галочки
   не является отказом от ГТД. Выбранный отказ передаётся как `is_gtd_absent: true`
   без `gtd`; номер — с `is_gtd_absent: false`. Изменения сохраняются автоматически.
5. Когда обязательные значения заполнены, в той же транзакции сохраняется полный
   неизменяемый пакет и задание передачи. Ожидание показывается как проверка данных.
   ГТД и ЧЗ имеют отдельные результаты: ГТД может быть отклонена при принятом ЧЗ.
6. В текущем окне «Завершить сборку» доступно после товарных сканов и подтверждения
   всех требуемых данных. Вызов `ship` выполняет отдельная операция готовности,
   модуль экземпляров не меняет статус отправления самостоятельно.

«М» остаётся единственным индикатором ЧЗ у товара: серая — скан/подтверждение ещё
не завершены, красная — код не прошёл проверку, зелёная — текущая привязка
подтверждена Ozon. Для нескольких единиц зелёный цвет появляется после подтверждения
всех их кодов. Ошибка ГТД отражается у её поля и блокирует завершение; она сама
по себе не делает принятый ЧЗ ошибочным. В уже готовом отправлении зелёный цвет
требует подтверждения применённых данных, а не только подготовленного обновления.

## Источники требований

Адаптер получает `/v6/fbs/posting/product/exemplar/create-or-get`, свежие
`requirements` и `optional` из `/v3/posting/fbs/get`. Исторические положительные
подсказки из списка заказов не заменяют этот результат. Отсутствие требования в
неполном ответе не означает, что данные не нужны. Неизвестные существенные флаги,
ошибка доступа, неполный состав и неоднозначные ID останавливают активацию.

- `is_mandatory_mark_needed`: исходное требование площадки.
- `is_mandatory_mark_possible`: исходная возможность; по согласованной политике
  панели такой ЧЗ **тоже обязателен**. В БД сохраняются исходная обязательность,
  итоговая политика и её версия 2, без подмены «можно» на «требует площадка».
- `is_gtd_needed` и свежий `products_requiring_gtd`: отдельное требование ГТД.
- РНПТ, вес, IMEI и страна учитываются отдельно. Уже присутствующие данные
  сохраняются в полном пакете. Если обязательных данных нет, пользователь должен
  указать их в кабинете Ozon и повторить сверку: редактора этих полей пока нет.
  Ввод УИН для обычных товаров не запрашивается. Уже переданные УИН сохраняются
  в полном пакете и проверяются как другие существующие маркировки.

Если после сборки положительный флаг исчез, прежнее требование панели сохраняется
для тех же SKU и `exemplar_id`. Исходное значение `cis_market` остаётся свежим.

Экземпляры сопоставляются по SKU, количеству и `exemplar_id`. Порядок массива в
ответе не определяет привязку существующего кода. При новых физических единицах
ID закрепляются детерминированно; последующая смена ID или распределения требует
сверки, а не переноса кодов по индексам массива.

## Методы и подтверждение

| Метод | Использование |
| --- | --- |
| `/v3/posting/fbs/get` | Свежий состав, статус, требования; для готовых — применённые экземпляры |
| `/v6/fbs/posting/product/exemplar/create-or-get` | Полный состав, идентификаторы и требования |
| `/v5/fbs/posting/product/exemplar/validate` | Предварительная проверка при наличии любой маркировки в полном пакете |
| `/v6/fbs/posting/product/exemplar/set` | Единственная попытка записи после сохранённого намерения |
| `/v5/fbs/posting/product/exemplar/status` | Опрос результата с проверкой ID, полных кодов, значений и ошибок |
| `/v1/fbs/posting/product/exemplar/update` | Применение данных к отправлению `awaiting_deliver` |

Перед записью снова читаются состав и поля площадки. Изменения другого оператора
не затираются: если свежие данные не совпадают с известным исходным, целевым или
подтверждённо отклонённым предыдущим набором, операция останавливается для сверки.
В каждый `set` входят **все продукты и все экземпляры**, включая немаркируемые;
вес, РНПТ, ГТД и другие маркировки не выбрасываются из пакета.

В `awaiting_packaging` окончательное подтверждение этого этапа — `ship_available`
и успешные проверки точных текущих значений. Сборка через `ship` ещё не выполняется.
В `awaiting_deliver` после подтверждения набора и `update_available` вызывается
`update`; затем проверяется фактическое сохранение через `get`. Оба метода записи
допускают пустой HTTP 200: это квитанция, а не зелёная «М». Уже сохранённые точные
данные могут быть подтверждены чтением без повторной записи.

Для явного «Не указывать» выполняется `set`: начальный `is_gtd_absent: true`
из созданного пустого экземпляра не заменяет передачу выбора сборщика. Пакет
без маркировок пропускает `validate` и проходит обычные `set`/`status`/`update`.
Подтверждение отказа требует совпадения ID, `is_gtd_absent: true`, отсутствия
номера и ошибок. Промежуточный/неизвестный статус не подтверждает отказ. В готовом
отправлении проверяется также применённое значение из `get`. Выбор сохраняется
при разделении вместе с той же физической единицей.

Проверки отдельных полей относятся к конкретным ID и значениям. `valid=true`
из `validate` не является проверкой оборота ЧЗ. `passed`/`success` проверяется
вместе с полным кодом и ошибками; неизвестный общий статус, старый результат,
другой криптохвост или отсутствующий экземпляр не подтверждают новый пакет.
Для IMEI/УИН и других данных, которых недостаточно в фактическом ответе для
надёжной сверки, подтверждение не выдумывается.

## Надёжность и границы модулей

- `assembly` принимает команды с UUID, арендой и ревизией, выбирает конкретную
  проверяемую единицу. Повтор HTTP не создаёт новый скан или привязку.
- `instance_data` хранит требования, значения по единицам, зашифрованные
  неизменяемые пакеты и результаты по полям. Задания — `instances.discover`
  и `instances.submit`; payload очереди содержит только UUID.
- `marking` хранит GTIN, серию, зашифрованный полный код, текущую/историческую
  привязку и результаты передачи. База запрещает две текущие привязки одного
  кода во всей установке и два текущих ЧЗ у одной физической единицы.
- `integrations.ozon.instances` содержит ограниченный клиент экземпляров.
  Прежний `OzonTransport.read` по-прежнему запрещает изменение экземпляров и сборку.
- `orders` остаётся владельцем физических единиц и распределения; соседние
  модули используют его публичные операции.

HTTP не выполняется внутри транзакции. Перед каждым сохранением результата
проверяются токен задания, ключи кабинета, состав, значения и исходные ID.
Переход между двумя рабочими статусами при прежнем составе допускается; выход
из рабочего состояния или изменение данных останавливают прежнюю операцию.

До HTTP-записи фиксируется намерение `set_started_at` или `update_started_at`.
После таймаута, 5xx, потери аренды или неясного ответа повторный исполнитель
**только сверяет результат**, не повторяет ту же запись. Однозначный HTTP-отказ
4xx отличается от неопределённого исхода; 429 допускает ограниченный повтор
после задержки и новой сверки. Опрос ограничен числом попыток и временем.
Неподтверждённый исход остаётся «Результат не подтверждён»; кнопка «Проверить
данные» запускает сверку. Если невозможно доказать исход, нужна сверка в кабинете,
а автоматическое освобождение или повторная отправка не выполняются.

Отмена локального окна сохраняет назначения и историю. Уже сохранённое задание
передачи/сверки не считается отменённым на площадке. При повторном открытии
незавершённый пакет может быть продолжен при той же ревизии ключей и состава,
без второго `set`. Смена этих оснований требует отдельной сверки. Ручная отвязка,
освобождение по возвратам и интеграция документов будут следующими этапами.

Если новое полное чтение после отмены подтверждает, что ранее принятый ЧЗ удалён
или заменён в кабинете, прежний код исключается из текущей единицы и не загружается
обратно автоматически. Его резерв сохраняется до подтверждения замены.

При конфликте используется сообщение:
**«Данный Честный знак уже используется в заказе: {номер отправления}»**.
Одинаковый GTIN/серия с отличающимися полными данными также не перезаписывает код.
Подтверждённый отказ конкретного кода позволяет заменить его, сохранив историю;
ошибка только ГТД не является разрешением заменить или освободить ЧЗ.
Снятие с текущей единицы (`retired_at`) отделено от освобождения резерва
(`released_at`). У единицы один текущий код, старые привязки остаются историей.
Только подтверждённый полный пакет с новым кодом освобождает старые резервы,
которых больше нет в нём. Неопределённый исход сохраняет блокировку. Старый
положительный результат не подтверждает повторно активированную ревизию привязки.
Повторный скан того же отклонённого кода создаёт новую попытку без второго
назначения; исправление/повтор ГТД не требует повторного скана принятого ЧЗ.

Откат миграции `0009_marking` блокируется, если есть резервы, ожидающие
подтверждения замены: старая схема не может безопасно представить это состояние.
Миграция не освобождает такие коды и не активирует их заново ради отката.

## Сканер и конфиденциальность

Поддержаны исходные GS1 с ASCII 29, префиксы `]d2`/`]d8`, печатное обозначение
`<gs>`/`<GS>`/`\<gs>`, известные компактный профиль 93 и фиксированный профиль
91/92 без разделителей. Неизвестные границы, оборванный код и буквальная строка
`\\u001d` не «исправляются» догадкой. Сохраняются регистр, кавычки, GS и криптохвост.
Клиент обрабатывает клавиатурный GS (`Ctrl+]`) только в поле сканирования.
Сериализация JSON экранирует реальный GS один раз, без двойного экранирования.

GTIN ЧЗ извлекается из AI 01, серия — из AI 21, проверяется контрольная цифра.
Для сравнения берутся типизированные GTIN каталога/сопоставленной карточки.
Цифры из OZN/MRKT не превращаются в GTIN. При неизвестном GTIN локальное
совпадение не выдумывается; окончательная проверка остаётся у площадки.

Полные коды и защищённые пакеты находятся в зашифрованных столбцах. Они не
возвращаются в обычный JSON/HTML сборки, аудит или ошибки. Скан в поле ГТД
отклоняется как неверный тип данных. Браузер хранит незавершённые значения только
в памяти: `sessionStorage` содержит метаданные команды, без ЧЗ и ГТД. После
потери ответа прежняя команда восстанавливается по UUID; незавершённое значение
пользователь вводит повторно. Черновик ГТД и фокус не теряются при опросе состояния.

## Проверка и обновление

Нужны миграция `0006_instances`, новый веб-процесс и worker из той же версии.
Проверки только товарных сканов alpha6 становятся историческими; их нельзя
считать подтверждением дополнительных данных. Действующие старые окна требуют
повторного открытия. Товарные факты и физические единицы сохраняются.

Тесты используют отдельную PostgreSQL `*_test` и mock HTTP: фактические
ограничения БД, две одинаковые единицы, два кабинета, гонки, полные пакеты,
отказы, различающиеся криптохвосты и потерю ответов на запись/применение.
`tests/browser_smoke.py --check-assembly` дополнительно проверяет поля ГТД,
клавиатурный GS, зелёную «М», восстановление и повтор после потери ответа.
Для этого нужен отдельный экземпляр с синтетическим Ozon и работающим worker.
Физическая печать и работа с производственным кабинетом этим этапом не проверялись.

Контракт сверялся с [публикацией снимка OpenAPI](https://github.com/MissiaL/ozon-api/blob/2f240188c7a6fec4d4c185eb2b6bc935c2c7983b/references/ozon-seller-openapi.json)
от 18.10.2026. Это сторонняя публикация официальной схемы; примеры переписки
не использовались как перечень допустимых типов или статусов.
