# Сборка, грузоместа и ярлыки Яндекс Маркета FBS

Версия `2.0.0a15`, миграция `0014_yandex_fulfillment`.
Все изменения находятся в `v2/`, используется отдельная PostgreSQL.
После обновления примените миграции, перезапустите web и worker одной версии.
Уже открытое окно сборки рекомендуется закрыть и открыть заново для свежей сверки.
Контракты сверены с официальным OpenAPI, снимок
`fbf491ab9461699bf242d21dd029a83a98010ee8`:
[репозиторий документации](https://github.com/yandex-market/yandex-market-partner-api).

## Методы

| Назначение | Метод |
| --- | --- |
| Авторитетное состояние, состав, требования, коробки и их идентификаторы | `POST /v1/businesses/{businessId}/orders` |
| Полная раскладка и данные экземпляров | `PUT /v2/campaigns/{campaignId}/orders/{orderId}/boxes` |
| Проверка конкретных ЧЗ | `POST /v2/campaigns/{campaignId}/orders/{orderId}/identifiers/status` |
| Готовность | `PUT /v2/campaigns/{campaignId}/orders/{orderId}/status` |
| Оригинальный PDF конкретной коробки | `GET /v2/campaigns/{campaignId}/orders/{orderId}/delivery/shipments/{shipmentId}/boxes/{boxId}/label?format=A7` |

Идентификаторы кампании, отгрузки, коробок и их штрихкоды берутся из ответа
площадки. Магазин не подставляется по умолчанию. Campaign ID — общая метаинформация магазина,
он не считается уникальным идентификатором заказа; миграция исправляет этот признак
у ранее сохранённых ссылок Яндекса. Для FBS не применяется устаревающий
метод `.../delivery/shipments/{shipmentId}/boxes`, помеченный в документации как DBS.

## Грузоместа

Внизу товаров находится небольшая кнопка «Добавить грузоместо».
После нажатия открывается редактирование с прежними карточками и перетаскиванием;
кнопка меняется на «Сохранить». Новый пустой блок позволяет создавать следующие места.
Пустые места и потеря товара при сохранении отклоняются сервером. Каждое изменение
получает собственную ревизию; возврат к прежнему варианту не переиспользует старое
подтверждение вместо новой передачи.

- Для обычных товаров перетаскивание переносит физическую единицу в другую коробку.
- Если в заказе одна единица, добавление места делит её на две части автоматически.
  Повторное добавление увеличивает число частей.
- Для части товара в составе большого заказа используется перенос с Alt.
  Клавиатурный перенос поддерживает Ctrl + стрелку; с Alt создаётся часть.
- Одна коробка с частью товара не смешивается с целыми товарами.
- Один многоместный товар сканируется один раз. Его ЧЗ и ГТД повторяются во всех
  частях запроса; количество проданных единиц не увеличивается.
- Неоднозначные несколько одинаковых многоместных товаров требуют сверки в кабинете.

По актуальному FBS-контракту раскладка редактируется только в
`PROCESSING/STARTED`, до «Готов к отгрузке». После `READY_TO_SHIP` редактирование
закрыто на клиенте и сервере.

Черновик хранится в зашифрованном контексте текущей сборки. При сохранении передаётся
полный набор коробок, экземпляров, ЧЗ и ГТД с `allowRemove=false`. Если обязательные
данные ещё не заполнены, черновик сохраняется локально и отправляется после их ввода.
Физические единицы и их коды не создаются заново из-за появления дополнительной части.

После изменения раскладки старый PDF и подготовленные для него задания печати
становятся недоступны. Новые ярлыки получаются после подтверждения раскладки.
Отмена окна и повторное открытие начинают сверку с площадкой: удалённое в кабинете
разделение не восстанавливается из старого локального черновика.

## Подтверждение готовности

После сканирования всех физических единиц и подтверждения ЧЗ/ГТД сборщик сканирует
стикер отправления либо нажимает «Завершить сборку». Сканирование служебного Campaign ID
или внутреннего хеша раскладки завершить сборку не может.

Панель повторно проверяет состав, кампанию, раскладку, данные экземпляров и статусы
конкретных кодов. Для обязательного по политике панели `CIS_OPTIONAL` также нужен `OK`
с доказательством сохранения полного кода. ГТД проверяется отдельно точным чтением.

Намерение изменения статуса фиксируется в БД перед HTTP. Передаётся:

```json
{"order":{"status":"PROCESSING","substatus":"READY_TO_SHIP"}}
```

Ответ 200 не завершает сборку в панели. Пока бизнес-API не подтвердит
`PROCESSING/READY_TO_SHIP` с тем же составом и данными, окно показывает обработку.
Уже готовый заказ подтверждается чтением без повторного PUT.

Таймаут или повреждённый ответ оставляют неизменяемое намерение: worker только
сверяет состояние, а не повторяет PUT. Проверка ограничена числом попыток и временем;
после этого доступна ручная сверка. Отмена окна после отправки не отменяет запрос на
площадке, но сохраняет возможность проверить результат без повторной отправки.
Изменение данных во время незавершённой операции закрыто.

## Получение, архив и печать

Оригиналы можно получить для актуальной раскладки до готовности, когда площадка
уже назначила Shipment ID и Box ID. До подтверждения необходимых данных сохраняется
метаданная запись для истории ЧЗ без выдачи неподтверждённого PDF.

Каждый ярлык запрашивается по собственному Box ID. Это исключает предположение,
что порядок страниц общего PDF совпадает с порядком коробок. Проверяются PDF,
одна страница на коробку, размер ответа, неизменность заказа до и после получения,
а также ревизии ключа и задания. Порядок коробок нормализуется по Box ID:
перестановка массива API не меняет соответствие страницы и физической единицы.
HTTP выполняется вне транзакций БД.

В «Стикерах» остаётся один текущий общий PDF заказа, собранный из оригинальных
страниц без перерисовки этикеток. История версий не создаётся. Доступны открытие,
скачивание, печать и прежняя история ЧЗ. Число страниц равно числу грузомест.

В настройках принтеров добавлен документ «Яндекс Маркет: ярлыки». Бумага,
ориентация, QZ Tray, браузер и подгонка используют прежний механизм. Размер оригинала
в этом этапе — A7. Принтер дубликата ЧЗ остаётся одним общим для всех площадок.

Автоматическая печать учитывает конкретное грузоместо: сначала должны быть
отсканированы все его товары. Для одного товара в двух местах печатаются обе
страницы после одного скана. Повторный опрос страницы не создаёт повторную отправку.
При включённой настройке ШК товара перед ярлыком выбирается `MRKT…`, затем другой
доступный код или собственный из сопоставленной карточки. Если кода нет, страница ШК
не добавляется. При печати части берутся ШК только товаров её коробки.

При неизвестном ответе принтера автоматического повтора нет: используются существующие
сообщения и ручная перепечатка. Повторная печать из архива остаётся явным действием.

Проверки используют синтетические ответы API, отдельную PostgreSQL и Chromium.
Живые заказы, ключи и физические принтеры при разработке не использовались.
