# Новая панель: каталог, заказы и сборка Ozon

Разработка ведётся в `refactor/modular-architecture`. Каталог `v2/` — отдельное
приложение; исходные `app/`, `data/`, зависимости и скрипты старой панели не меняются.
Дизайн использует прежние цвета, формы и расположение меню.

В этой поставке работают авторизация, серверные сессии, роли/доступы, создание
пользователя через защищённый API, оболочка разделов, миграции PostgreSQL и
базовый исполнитель сохранённых заданий. Есть модели каталога, заказов,
отправлений и грузомест с ограничениями целостности.

В «Настройки → Кабинеты» доступны добавление Ozon, изменение названия,
замена Api-Key, включение/отключение и ручная проверка доступа. Сохранение
и проверка — разные действия; при сохранении запросы к Ozon не выполняются.

Добавлен [адаптер чтения Ozon](docs/ozon-reader.md): каталог со штрихкодами,
FBS-отправления и поиск по коду стикера, включая `ii…`. Он возвращает общие
снимки для бизнес-модулей. [Модуль каталога](docs/catalog-sync.md) сохраняет
карточки и штрихкоды в PostgreSQL и показывает их в разделе «Товары».
[Модуль заказов](docs/orders-sync.md) загружает FBS-отправления, их состав,
сопоставление с каталогом и показывает список/карточку отправления.

[Модуль сборки](docs/assembly-verification.md) открывает отправление после фоновой
сверки с Ozon, принимает штрихкоды каждой физической единицы, сохраняет прогресс
и подтверждает готовность отправления через [операцию Ozon](docs/ozon-readiness.md). Есть защита от повторных запросов и
одновременной работы двух сборщиков. Версия `2.0.0a8`, схема `0007_readiness`.

[Данные экземпляров и Честный знак](docs/instance-data.md) получают требования
Ozon, запрашивают ЧЗ каждой единицы и ГТД, передают полный пакет и проверяют
результат. Доступный необязательный ЧЗ тоже обязателен по политике панели.
«М» отражает подтверждение конкретной привязки; ГТД имеет отдельный результат.

**Разделение, печать и перенос старых данных ещё не подключены.**
Другие рабочие разделы показывают состояние разработки. Веб-страницы читают
локальную БД, запросы каталога и заказов к Ozon выполняет отдельный worker. Старую SQLite
эта поставка не читает и не изменяет.

## Кабинеты и ключи

Доступ есть у владельца и администратора. Client-Id и Api-Key зашифрованы
отдельным ключом новой панели; Api-Key не возвращается в HTML/JSON и не
попадает в аудит, сообщения ошибок или ответы проверки. Пустое поле нового
Api-Key сохраняет прежний ключ. Смена ключа сбрасывает подтверждение доступа.

Client-Id закрепляется за кабинетом при создании. Другой Client-Id означает
новый кабинет; так заказы одного продавца не будут переименованы в чужие.
Повтор такого же Client-Id блокируется, в том числе для отключённого кабинета.
Отключение сохраняет ключи и историю; удаления данных в этом этапе нет.

«Проверить доступ» делает по одному запросу чтения с `limit=1`:

- `/v4/posting/fbs/list` — заказы FBS за последние сутки;
- `/v3/product/list` — каталог;
- `/v1/returns/list` — возвраты.

Показывается отдельный результат по каждому разделу. HTTP 403 означает
отсутствие доступа к конкретному чтению; таймаут/429 не объявляются неверным
ключом. Проверка чтения не подтверждает права на сборку, изменение заказов,
экземпляры и маркировку. Методы изменения отправлений и создания экземпляров
не вызываются. Исходные записи товаров/заказов при этой проверке не сохраняются.

Проверка выполняется вне транзакции БД. Для одного кабинета действует аренда
проверки, а результат привязан к ревизии ключей: ответ на старый ключ не
подтверждает новый. Прерванная проверка допускает повтор после истечения аренды.

## Запуск с нуля для разработки

Нужны Python 3.12+ и отдельная PostgreSQL 17. Команды ниже выполняются из `v2/`.

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.lock
.venv/bin/pip install --no-deps -e .
.venv/bin/python -m pack_v2 generate-env
docker compose --env-file .env.v2 up -d --wait postgres
.venv/bin/python -m pack_v2 --env-file .env.v2 migrate
.venv/bin/python -m pack_v2 --env-file .env.v2 create-owner --login admin
.venv/bin/python -m pack_v2 --env-file .env.v2 check
.venv/bin/uvicorn pack_v2.bootstrap.app:create_app --factory --env-file .env.v2 --host 127.0.0.1 --port 8001
```

Пароль вводится интерактивно и не передаётся аргументом процесса. Первый
владелец создаётся только CLI, публичного маршрута регистрации владельца нет.
`generate-env` создаёт файл с правами 0600 и отказывается перезаписывать его.

Если PostgreSQL уже установлен, Docker не нужен: создайте отдельную базу и
пользователя v2, укажите их в `PACK_V2_DATABASE_URL`. SQLite и другие драйверы
отклоняются настройками. Не направляйте тесты на рабочую базу.

Приложение читает только переменные `PACK_V2_*`. CLI читает файл только через
`--env-file`; веб-сервер — через явно переданный ему `--env-file .env.v2`.
Старый корневой `.env` автоматически не читается. Схема PostgreSQL — `pack_v2`;
миграции не меняют таблицы в `public` и не запускаются автоматически при старте веба.

Для публикации настройте HTTPS, разрешённые имена хоста,
`PACK_V2_ENVIRONMENT=production` и `PACK_V2_SECURE_COOKIES=true`.
Используйте собственный reverse proxy/service для v2; старые deploy-скрипты
относятся к прежней панели. Эта поставка не переключает работающий сервер.

Для обновления уже установленной **v2**, из её каталога:

```bash
.venv/bin/pip install -r requirements.lock
.venv/bin/pip install --no-deps -e .
.venv/bin/python -m pack_v2 --env-file .env.v2 migrate
```

Затем перезапустите отдельный процесс v2. Существующий `.env.v2` и его ключ
шифрования сохраняются; повторный `generate-env` при обновлении не нужен.

## Фоновый процесс

```bash
.venv/bin/python -m pack_v2 --env-file .env.v2 worker
```

Веб-процесс не запускает фоновые потоки. Зарегистрированы идемпотентная очистка
истёкших сессий/ограничителей входа, `catalog.sync` и `orders.sync` для чтения Ozon,
`instances.discover` и `instances.submit` для требований/передачи экземпляров,
`assembly.ready` для подтверждения готовности Ozon.
Кнопка «Обновить товары» ставит задание в очередь и сразу возвращает страницу.
Активные кабинеты также обновляются фоновым процессом каждые 15 минут;
`PACK_V2_CATALOG_SYNC_MINUTES=0` отключает автоматический запуск, сохраняя ручной.
Заказы обновляются каждые 5 минут; `PACK_V2_ORDERS_SYNC_MINUTES=0` оставляет
только ручной запуск. По умолчанию окно истории — 30 дней. Периодическая полная
загрузка чередуется с загрузкой активных и точечной сверкой исчезнувших отправлений.
Подробности и ограничения — в [описании заказов](docs/orders-sync.md).
Без запущенного worker задания остаются в состоянии «В очереди». В очередь можно
добавлять задания внутри транзакции через `infrastructure.jobs.enqueue`.
Захват использует `FOR UPDATE SKIP LOCKED`, аренду и токен исполнителя;
запоздалое завершение другой аренды отклоняется. Неизвестный обработчик
помечается ошибкой, а не исполняется произвольно.

Внешние операции с неоднозначным результатом не подключаются к обычным
автоматическим повторам. Передача экземпляров и готовность Ozon используют
сохранённые намерения, сверку фактического результата и контроль ревизий. Для длительной загрузки
каталогов worker продлевает аренду отдельными короткими
транзакциями; каждая запись дополнительно проверяет токен аренды и ревизию ключей
в той же транзакции, в которой сохраняется порция карточек.

## API и доступ

- `GET /healthz` — процесс работает, без проверки БД.
- `GET /readyz` — PostgreSQL доступна и миграция соответствует приложению.
- `GET /api/v2/me` — текущий пользователь и CSRF-токен; только после входа.
- `GET /api/v2/modules` — состояние модулей; администратор/владелец.
- `POST /api/v2/users` — создание сотрудника; JSON с `login`, `password`, `role`,
  `sections`, заголовок `X-CSRF-Token`. Сборщик не создаёт пользователей,
  администратор не создаёт владельцев.
- `POST /logout` — завершение сессии с CSRF. GET не завершает сессию.
- `GET /api/v2/accounts` — кабинеты без Api-Key; владелец/администратор.
- `POST /api/v2/accounts` — добавить Ozon: `title`, `client_id`, `api_key`.
- `PATCH /api/v2/accounts/{id}` — `revision`, `title`, необязательный новый `api_key`.
- `POST /api/v2/accounts/{id}/active` — `revision`, `active`.
- `POST /api/v2/accounts/{id}/check` — `revision`; вернуть результаты чтения.
- `GET /api/v2/orders` — отправления из БД, поиск и фильтры; разрешение «Заказы».
- `GET /api/v2/orders/{id}` — состав и связанные отправления.
- `GET /api/v2/orders/sync` — состояние загрузок заказов.
- `POST /api/v2/orders/sync` — поставить загрузку в очередь; администратор/владелец, CSRF.
- `GET /api/v2/products` — карточки из БД; доступ к разделу «Товары».
- `GET /api/v2/catalog/sync` — состояние загрузок; доступ к товарам или настройкам.
- `POST /api/v2/catalog/sync` — поставить загрузку в очередь; JSON `{}` для
  активных кабинетов или `{"account_id":"UUID"}` для одного; администратор/владелец, CSRF.

Изменяющие API-запросы требуют `X-CSRF-Token`. Старые ревизии отклоняются
конфликтом, ошибка валидации не возвращает исходное тело с ключами.

Владелец имеет полный доступ; у администратора есть настройки, а доступ к
рабочим разделам задаётся отдельно. Сборщик видит разрешённые разделы и
может открыть страницу принтеров. Роли, права и активность читаются из БД;
смена `auth_revision` немедленно закрывает прежние сессии. Пароли хешируются
Argon2id; в БД лежит только отпечаток случайного токена сессии.

## Проверка

```bash
.venv/bin/pip install -r requirements-dev.lock
export PACK_V2_TEST_DATABASE_URL='postgresql+psycopg://USER:PASSWORD@127.0.0.1:55432/pack_v2_test'
.venv/bin/pytest
.venv/bin/ruff check src tests
```

Для проверок нужна **отдельная** база с именем, заканчивающимся на `_test`.
Тесты очищают только её схему `pack_v2`. Проверяются реальные миграции,
ограничения PostgreSQL, права, CSRF, выход, отзыв сессий, лимиты входа,
конкурирующие задания и изоляция кода от старого приложения.
Проверки API площадки используют только `httpx.MockTransport`: реальные ключи
и доступ к старой панели не нужны. Сетевые HTTP-вызовы в тестах заблокированы.

Браузерная проверка на отдельном запущенном экземпляре с тестовым владельцем:

```bash
.venv/bin/python tests/browser_smoke.py --url http://127.0.0.1:8001 --login admin --chromium /usr/bin/chromium
```

Пароль запрашивается интерактивно. Проверяются вход/выход, меню при наведении
и клике, настоящие касания, мобильная ширина и отсутствие ошибок JavaScript.
Скриншоты сохраняются в игнорируемый `test-results/`.
Флаг `--check-accounts` дополнительно проверяет создание, переименование,
проверку доступа, замену ключа и отключение синтетического кабинета. Используйте
его только на отдельном тестовом экземпляре с подменёнными ответами Ozon.
Флаг `--check-catalog` дополнительно проверяет загрузку, отображение прогресса,
поиск и мобильную таблицу. Для него нужны подменённый адаптер и запущенный
worker на том же отдельном тестовом экземпляре.
Флаг `--check-orders` проверяет список, карточку, поиск `ii…` и связи отправлений
при тех же условиях. Используйте синтетические ответы и отдельную БД.
Флаг `--check-assembly` проверяет сканирование, восстановление прогресса,
потерю ответа после фиксации скана и быстрые последовательные сканы.
Он требует тот же отдельный экземпляр с mock Ozon и работающим worker.

План и правила переноса: [проект архитектуры](../docs/architecture-v2-proposal.md).
Подключена [готовность Ozon](docs/ozon-readiness.md) после проверки товаров и данных.
Следующий этап — разделение; затем документы и печать.
Локальная проверка товаров не подменяет эти операции.
