# Ozon Pack — панель сборки заказов Ozon и Avito

Веб-панель для склада: подтягивает заказы и возвраты из Ozon Seller API и заказы
из Avito API, ведёт сборщика по процессу так, чтобы он **не мог** взять не тот
товар, положить его не в то отправление или собрать одно отправление дважды.

Магазинов может быть несколько — это **кабинеты**. У каждого свои ключи и свои
данные; кабинет выбирается списком в шапке панели. Заказы, товары и штрихкоды
разных кабинетов не пересекаются, поэтому товар одного магазина невозможно
положить в отправление другого.

Разворачивается на VPS, открывается по IP-адресу в браузере: `http://IP-сервера:8080`.

## Как устроен процесс сборки

```
  «Ожидает сборки»                    «Ожидает отгрузки»                     Готово
        │                                     │                                │
        │ 1. Кнопка «Собрать»                 │ 2. Скан товара или стикера     │
        │    (v4/posting/fbs/ship)            │    → система сама находит      │
        │                                     │      отправление и его состав  │
        ▼                                     │    → стикер на печать, если    │
   Заказы FBS ─────────────────────────────►  │      его ещё нет на руках      │
                                              │ 3. Упаковали, наклеили стикер  │
                                              │ 4. Скан стикера отправления ───┘
```

**Что панель не даст сделать:**

| Ошибка | Как блокируется |
|---|---|
| Взяли не тот товар | Скан товара, которого нет в активном отправлении → красный экран «СТОП», товар не засчитывается |
| Положили товар не в то отправление | Закрыть отправление можно только сканом **его** стикера; чужой стикер → «СТОП» |
| Положили лишнюю штуку | Скан сверх нужного количества → предупреждение со звуком |
| Собрали дважды | Собранные отправления исчезают из подбора, повторный скан стикера → предупреждение с именем сборщика и временем |
| Двое собирают одно отправление | Отправление закрепляется за сборщиком на `CLAIM_TTL_MINUTES` минут |
| Закрыли, не собрав всё | Скан стикера до сканирования всех товаров → отказ со списком недостающего (`REQUIRE_ALL_ITEMS=1`) |

Каждое действие пишется в журнал (`/logs`): кто, что, когда, какой код отсканировал —
по нему разбираются спорные случаи.

## Кабинеты

Кабинет — магазин на площадке. Добавляются в **Настройках → Кабинеты**: выбрать
площадку (Ozon или Avito), задать название и ключи. Ключи проверяются до
сохранения — опечатка не оставит склад без данных.

| | Ozon | Avito |
|---|---|---|
| Ключи | Client-Id и Api-Key (Настройки → Seller API) | client_id и client_secret (Настройки → Профиль → API) |
| Разделы | Сборка, Заказы FBS, Возвраты | Заказы Avito, Возвраты |
| Синхронизация | отправления, товары, возвраты | заказы в рабочих статусах и возвраты к выдаче |

Переключение — списком в шапке. Разделы меняются вместе с кабинетом: в кабинете
Avito не показываются FBS и возвраты, в кабинете Ozon — раздел Avito. Журнал и
настройки общие, но журнал показывает события текущего кабинета.

Удаление кабинета удаляет и его данные — заказы, товары, штрихкоды, возвраты.
Последний кабинет удалить нельзя.

## Разделы

### 1. Сборка (`/pack`) — рабочее место сканера

Одно поле ввода, всегда в фокусе. Сканер работает как клавиатура — специальных
драйверов не нужно, достаточно настроить в нём суффикс **Enter** после кода.

* Скан штрихкода товара → панель показывает отправление и **весь его состав**,
  автоматически отправляет стикер на печать.
* Если товар нужен в нескольких отправлениях — показывается список, отсортированный
  по сроку отгрузки (выбор мышкой или цифрой 1–9 на клавиатуре).
* Прогресс «собрано N из M», у каждой позиции — артикул, SKU, штрихкоды, отметка
  «Честный знак».
* Скан стикера отправления закрывает сборку. Звуковые сигналы: успех, предупреждение, ошибка.
* **Начать можно и со скана стикера** — если он уже напечатан и лежит с заказом.
  Тогда панель открывает отправление, но на печать стикер не отправляет: он у
  сборщика в руках. Дальше всё как обычно — товары, потом стикер ещё раз.
* Кнопка «Завершить без скана стикера» — на случай нечитаемого стикера (попадает в журнал).

Понимаются коды: EAN-13/UPC (в том числе с ведущим нулём), SKU и артикул продавца,
DataMatrix «Честного знака» (из него извлекается GTIN), номер отправления,
штрихкоды стикера Ozon (`upper_barcode` / `lower_barcode`), а если код неизвестен
локально — панель спрашивает Ozon через `v2/posting/fbs/get-by-barcode`.

### 2. Заказы FBS (`/orders`)

Вкладки «Ожидает сборки» / «Ожидает отгрузки» / «Собранные». Массовые действия:
перевести выбранные в «Ожидает отгрузки» (`v4/posting/fbs/ship`) и напечатать пачку стикеров.
По каждому отправлению: срок отгрузки с подсветкой просрочки, состав, город и регион,
способ доставки и служба, склад, тип оплаты, метки Express / маркировка / многоместное,
кто сейчас собирает, печатался ли стикер.

### 3. Возвраты FBO/FBS (`/returns`)

Панель загружает из Ozon (`v1/returns/list`) возвраты в статусе
**«В пункте выдачи»** (`ArrivedAtReturnPlace`) — то есть те, что физически лежат
на пункте и их можно забрать. Список с фильтрами по схеме FBO/FBS, пункту выдачи
и поиском. Кнопка **«Печать листа»** формирует лист А4 со штрихкодами Code128,
колонкой для отметки и полями для подписей — с ним сборщик идёт получать
возвраты. В колонке «Пункт выдачи» печатается название и адрес ПВЗ; статуса на
листе нет — там и так всё, что можно забрать.

**Отметка о возврате — не здесь, а во вкладке «Ждёт подтверждения».** Возврат
из этого списка ещё лежит в пункте выдачи: его не то что не проверяли — его в
руках не держали, и решать по нему нечего. Отмечают привезённое, внутри акта.
Кнопка **«Отметить»** открывает окно, где возврат помечается как **принят** (✓)
или **не принят** (✗) и к нему пишется комментарий — вскрыта упаковка, нет
комплекта, не выдали. Отметку заводит панель, площадка о ней не знает: у Ozon и
Avito в статусах есть только «лежит в ПВЗ» и «уехал дальше». Поэтому
синхронизация отметку и комментарий не трогает — они не пропадут при обновлении
списка. Отметка попадает и на лист, и в журнал (кто поставил и когда), а «Снять
отметку» убирает её целиком. То же окно есть в разделе возвратов Avito.

На бумажном листе колонка для отметки остаётся — её и заполняют ручкой в ПВЗ,
а в панель переносят потом.

**Ждёт подтверждения.** Забранный возврат Ozon перестаёт отдавать как «В пункте
выдачи», и строка уходила с экрана ровно тогда, когда сборщик заканчивал
проверку и шёл записать результат. Поэтому в разделе есть вторая вкладка, где
возвраты держатся до отметки.

Акт составляет человек. Актов о возвратах Ozon не отдаёт — своего документа,
по которому можно было бы собрать состав, у площадки нет. Признак получения —
статус самого возврата: **«Получен продавцом»** (`ReceivedBySeller`) означает,
что он уже у нас. Панель копит такие возвраты, но акт не заводит: когда поездка
закончилась, знает только сборщик.

**Два действия: выбрать дату и нажать «Составить акт»** (вкладка «Ждёт
подтверждения», у всех, кому открыт раздел «Возвраты», — ездит сборщик, он же
и составляет акт, не дожидаясь администратора). Сколько возвратов попадёт в акт,
панель считает сама при выборе даты и пишет прямо на кнопке — «Составить акт на
9». Дата, а не промежуток: акт — это поездка, а не отчётный период.

**Несколько актов за одну дату — это норма.** За возвратами ездят по разу за
партию, поэтому каждое нажатие делает **новый** акт, и в него попадает только
то, что ещё ни в один акт не вошло. Первый акт при этом не меняется: возврат из
него во второй не переезжает. Нажали, а нового ничего нет — кнопка заперта.
Акты одной даты различаются номером и временем прямо в заголовке: «Возвраты за
14.09.2026, акт №2 от 21:47».

**Задвоить возврат нельзя.** Возврат, попавший в акт, второй раз в акт не
попадёт: `act_id` ставится один раз и не снимается даже после подтверждения.
Это проверяется отдельно: при любом порядке нажатий сумма позиций по всем актам
равна числу строк с актом, а составы актов не пересекаются.

**Дата получения — от площадки, а не «сейчас».** По статусу «Получен» Ozon
отдаёт **весь архив**: возвраты, полученные месяцы назад, приходят в том же
ответе. Иначе первое же обновление объявило бы полученными сегодня тысячи
старых возвратов: в версии 1.17 так и вышел акт на 2446 позиций за одну минуту.
Акты, оставшиеся от 1.17, при обновлении убираются (`_drop_auto_return_acts`),
а их возвраты возвращаются в работу — кроме строк с отметкой сборщика, их
трогать нельзя.

**Момент получения берётся из `logistic.final_moment`** — «возврат прибыл на
фулфилмент или выдан продавцу», то есть само получение. `visual.change_moment`
только запасной: это последняя смена статуса, а она бывает позже и уже в
других сутках. Выдали продавцу в 23:58, статус площадка перещёлкнула в 00:30 —
и по `change_moment` возврат уезжал в следующее число. Одна поездка
раскладывалась на два дня: шесть возвратов попадали в акт, седьмой нет. Числа
уже записанных возвратов пересчитываются при обновлении
(`_repair_received_days`) — всё, что ещё не в акте; строки с актом не трогаются,
там работа идёт.

Если момент получения не разобрать совсем, ставится сегодняшнее число: возврат
лучше положить в акт не за тот день, чем потерять с экрана. Раньше в поле числа
оседала сама строка от площадки — такого числа нет ни в одном календаре, и
возврат не находился ни при каком выборе даты.

Отметили все возвраты акта — его можно подтвердить, и он уходит в раздел
**«Отчёты» → «Акты возвратов»**, где видны состав, отметки, комментарии и кто
подтвердил. Пока хоть одна строка без отметки, кнопка заперта: иначе акт
закроют наполовину и никто не заметит. Отпирается она сразу после последней
отметки — шапка акта пересчитывается на месте, страницу обновлять не нужно.

**Переделать принятое может владелец**, и только открыв сам акт — из «Отчётов»
или из вкладки. Два разных действия:

* **«Вернуть в работу»** — акт уходит из «Отчётов» обратно в «Ждёт
  подтверждения» вместе с отметками. Это когда подтвердили рано и надо
  поправить одну-две строки.
* **«Удалить акт»** — акта не остаётся: возвраты освобождаются, отметки с них
  снимаются, и акт за то же число составляется заново. Это когда поездку надо
  принять с нуля. Момент получения не трогается — он факт площадки, поэтому
  возвраты тут же снова видны в «Составить акт» за своё число.

Отметки снимаются намеренно: акт из уже отмеченных строк подтвердился бы сразу,
и принимать в нём было бы нечего. В **«Журнале»** они остаются — каждая отметка
записана отдельным событием, как и само снятие подтверждения
(`return_act_unconfirm`) и удаление (`return_act_delete`). Администратору ни
того, ни другого не дают: иначе подпись владельца снималась бы без него. У акта свои **«Скачать акт PDF»** и
**«Печать акта»** — тот же лист, но уже с отметками и комментариями. Главная
вкладка не меняется: там по-прежнему только то, что лежит в ПВЗ.

**Два списка статусов, а не один.** «Какие возвраты загружать» — это список
сборщику к поездке (`ArrivedAtReturnPlace`). «Какие считать полученными» —
отдельная настройка (`ReceivedBySeller`), из неё набирается состав акта. Одним
списком это быть не может: включить акты значило бы показать сборщику то, за
чем ехать уже не надо. Статус, отмеченный в обоих, считается «к выдаче» —
класть в акт неполученное нельзя. Пустой список «полученных» выключает акты
совсем.

**Запасной путь.** Возврат пропал из выдачи, а «Получен» по нему не приходил —
такой попадает в акт «без статуса» за день, чтобы не исчез молча. Придёт
«Получен» и человек составит акт за эту дату — строка переедет туда: факт
точнее догадки, а два акта на один возврат означали бы две отметки на одну
работу.

**Скачать PDF.** Тот же лист можно взять готовым файлом — кнопка
**«Скачать PDF»** рядом с печатью. Пригодится, когда лист нужно переслать
водителю, сохранить к отчёту или напечатать там, где браузер печатает не то.
Файл собирается на сервере (`app/returns_pdf.py`), со штрихкодами Code128,
отметками и комментариями — в том же составе колонок, что и лист для печати.

Для PDF нужен шрифт с кириллицей: встроенные в PDF шрифты русские буквы не
показывают. `install.sh` ставит пакет `fonts-dejavu-core`; подойдут также
Liberation и FreeFont, а свой файл можно указать через `RETURNS_PDF_FONT`
в `.env`. Если шрифта не нашлось, панель прямо скажет, что поставить, — лист
по-прежнему печатается из браузера.

Фильтр по статусу уходит в запрос к Ozon, но панель на него не полагается: всё,
что пришло с другим статусом, отбрасывается на своей стороне и в базу не
попадает. Под списком видно, что именно вернул Ozon при последней синхронизации
и сколько записей скрыто — если API отдаст лишнее, это будет заметно сразу.

Когда возврат уезжает из пункта выдачи (забрали, отправили продавцу,
утилизировали), Ozon перестаёт отдавать его в этом статусе, и панель убирает
позицию из списка сама — поэтому ручная отметка «забрали» не нужна и её нет.
Сверка выполняется только после успешного обхода: сбой связи не обнулит список.

Набор статусов задаётся в **Настройках** панели (галочками, применяется сразу)
или через `RETURNS_READY_STATUSES` в `.env`. Значение из панели важнее файла.

**Печать по всем кабинетам.** Рядом с обычной кнопкой печати есть
**«Печать по всем кабинетам»** — один лист со всем, что готово к выдаче во всех
включённых кабинетах сразу, и Ozon, и Avito. За возвратами едут один раз, а
магазинов у склада обычно несколько, поэтому собирать поездку удобнее по одному
листу, чем переключать кабинеты и печатать по очереди.

Лист состоит из двух разделов: у Ozon строка — это позиция товара, у Avito —
заказ целиком с вложенными товарами, свести их в одну таблицу нельзя. В обоих
разделах появляется колонка **«Кабинет»**, а строки Ozon идут по пунктам выдачи,
чтобы возвраты одного ПВЗ шли подряд. Та же кнопка есть и на странице возвратов
Avito — лист общий.

Фильтры текущего кабинета (схема, пункт выдачи, поиск) на этот лист не
распространяются: на нём нужно всё, что можно забрать, иначе сборщик уедет за
частью возвратов. Если строк окажется больше, чем помещается в выборку, лист
об этом прямо напишет. Напечатанные позиции помечаются во всех задействованных
кабинетах сразу.

### 4. Заказы Avito (`/avito`) — кабинеты Avito

Две вкладки, ровно по двум задачам сборщика:

| Вкладка | Статус в Avito | Что делает кнопка |
|---|---|---|
| **Подтвердите заказ** | `on_confirmation` | `applyTransition confirm` — заказ переходит в «ждёт отправки». Если не подтвердить до срока, Avito отменит заказ сам |
| **Отправьте заказ** | `ready_to_ship` | `applyTransition perform` — подтверждение отправки |

Остальные статусы (в пути, доставлен, отменён, спор, возврат) панель **не
загружает и не показывает**: сборщику там делать нечего, а лишняя строка на
складе — лишняя ошибка. Как только заказ уходит из рабочего статуса, он
исчезает из списка.

Так же скрыты и остальные действия Avito API — отмена заказа, коды маркировки
«Честный знак», трек-номера DBS, интервалы приезда курьера, подтверждение
возврата. Кнопка «Отправить заказ» появляется только там, где Avito её
разрешает (доставка курьером продавца, RDBS); по остальным способам доставки
отправку отмечает сама площадка при приёме посылки.

**Печать этикеток.** Кнопка «Этикетка» печатает PDF, который отдаёт Avito
(`/order-management/1/orders/labels` → `.../download`), без какого-либо
редактирования на нашей стороне. Можно печатать пачкой — Avito принимает до
50 заказов за раз.

Строка заказа показывает: номер, срок, состав с артикулами, способ доставки,
ПВЗ или покупателя, трек-номер.

**Возвраты Avito** (`/avito/returns`) — то же правило, что и у возвратов Ozon:
в панели только то, что сборщик реально может забрать.

Панель хранит возвраты **единственного** состояния — «Заберите заказ»: посылка
доехала и лежит в пункте выдачи. Возвраты в пути и те, что продавец забирает
сам (DBS), не сохраняются и не показываются — забирать там нечего. Сколько
таких пришло при последней синхронизации, написано над списком: молча они не
исчезают.

> **Важно про написание.** В схеме Avito это состояние описано как
> `ready_to_pickup`, а боевой API отдаёт `ready_for_pickup` — через `for`.
> Расхождение настоящее, поэтому панель принимает **оба** написания. Если
> сверять только со схемой, все возвраты к выдаче отбрасываются как посторонние.

Отмечать что-либо вручную не нужно: как только кладовщик получил возврат в
пункте выдачи, Avito переводит заказ дальше сам, и ближайшая синхронизация
убирает его из панели. Раздел только читается — список, поиск и печать листа.

Кнопка «Печать листа» даёт лист А4 для похода в пункт выдачи: номер заказа,
трек-номер возврата штрихкодом, состав, количество, служба и адрес ПВЗ в
колонке «Пункт выдачи» и графы для подписей — так же, как лист возвратов Ozon.

Адрес ПВЗ в схеме Avito описан только для доставки партнёром продавца
(`delivery.terminalInfo`), но на практике площадка кладёт его и в другие поля.
Панель поэтому сначала смотрит известные места, а затем ищет адрес по всему
ответу; если адреса нет вовсе — печатает код ПВЗ, а если нет и его, честно
пишет «адрес Avito не прислал» вместо пустой клетки. Что именно пришло по
конкретному возврату, администратор может посмотреть целиком:
`/api/avito/returns/<номер заказа>/raw`.

### 5. Сборка Avito (`/avito/pack`) — рабочее место сканера

У Avito штрихкодов товаров нет: справочника площадка не отдаёт, сверять скан
не с чем. Поэтому порядок обратный тому, что на Ozon — сначала стикер, потом
товар:

1. сборщик печатает стикер отправления на вкладке «Заказы Avito»;
2. **сканирует стикер** — открывается сборка этого заказа с его составом;
3. **сканирует штрихкод товара** — свой, поставщика, любой, какой есть;
4. панель записывает его в отчёт вместе с номером отправления и названием
   позиции;
5. когда отсканированы все единицы, заказ помечается **собранным**.

Стикер опознаётся по номеру заказа, номеру на площадке, номеру отправления
или треку — что бы ни оказалось в штрихкоде.

Что панель проверяет, а что нет. Сверить товар не с чем, поэтому она не решает,
«тот» он или нет, — фиксирует, что именно приложили к этому отправлению.
Ошибкой считается скан стикера **другого** заказа посреди сборки: он попадает в
отчёт с пометкой и сборку не закрывает. Собранный заказ повторно не открывается,
заказ в статусе «Подтвердите заказ» собирать не даёт, а взятый в работу
удерживается за сборщиком, чтобы двое не собирали одно и то же.

Отправку в Avito сборка не делает — это по-прежнему отдельная кнопка
«Отправьте заказ» на вкладке заказов.

### 6. Отчёты об отгрузке (`/reports`)

Отчёт о том, что реально ушло со склада. Ключевое отличие от журнала: строка
появляется **не при открытии заказа**, а в момент, когда сошлась пара
«штрихкод товара → номер отправления»:

1. сборщик сканирует штрихкод товара — панель ищет его в ожидаемом составе;
2. сканирует номер отправления (или товар сам выбирает отправление) — панель
   сверяет, что этот товар должен уйти именно здесь;
3. только после совпадения пишется строка.

Что попадает в отчёт:

| Результат | Когда появляется |
|---|---|
| **Отгружен** | пара сошлась, товар зачтён — по строке на каждую единицу |
| **Штрихкод не опознан** | кода нет в справочнике Ozon — пишутся штрихкод, отправление и название товара |
| **Ошибка сборки** | взяли не тот товар, отсканировали стикер другого отправления, лишний скан сверх количества, товар не нужен ни в одном отправлении |

Ошибки видно отдельной колонкой с причиной — по ним и разбирают, где сборщики
путаются.

**Защита от дублей.** Одна единица товара в одном отправлении записывается
единожды, сколько бы раз её ни отсканировали: если отправление вернули в работу
и собрали заново, отчёт не раздувается. Ошибки, наоборот, пишутся все — три
попытки положить не тот товар должны быть видны как три.

**Отчётный день закрывается в заданное время** (по умолчанию 18:00 по Москве,
меняется в «Настройках»). Всё, что отсканировано после отсечки, попадает уже
в следующий день — так отчёт совпадает с фактической отгрузкой. День до отсечки
помечен «идёт сбор», после — «итоговый».

**Выгрузка** — кнопка «Скачать CSV» на любом дне или с фильтром по кабинету и
типу строк. Файл открывается в Excel двойным щелчком: разделитель `;` и BOM,
кириллица не рассыпается. Столбцы: отчётный день, время скана, кабинет,
площадка, отправление, артикул продавца, SKU, товар, штрихкод, номер единицы,
результат, причина, сборщик.

**Акты возвратов** (`/reports/returns`) — вторая вкладка раздела. Сюда уходит
подтверждённый акт получения: когда собран, кто подтвердил и когда, сколько
принято и сколько нет. Внутри акта — состав со всеми отметками и
комментариями, плюс те же PDF и печать. Обратно в «Возвраты» акт не
возвращается: работа по нему закрыта.

### 7. Товары (`/products`) — каталог и наборы

Раздел администратора. Поиск по названию, артикулу, SKU или штрихкоду.

**Кнопка «Обновить каталог»** перечитывает каталог кабинета у Ozon целиком
(`/v3/product/list` → `/v3/product/info/list`). Обычная синхронизация тянет
карточки только тех товаров, что встретились в заказах и возвратах — сборщику
больше и не нужно. Но набор собирают из складских остатков, а не из вчерашних
продаж, и для выбора нужен весь каталог.

Обход идёт в фоне: тысячи карточек за один запрос браузера не успеть, а
обрывать на середине нельзя — каталог останется наполовину старым. Кнопка
показывает, сколько уже прошло. Автоматически он не запускается: каталог
меняется редко, а гонять десятки запросов к Ozon каждые несколько минут
незачем — вы знаете, когда завели новый товар.

**Архивные товары не загружаются.** Ozon отдаёт их в том же ответе, что и
живые; панель их отсеивает и говорит, сколько отсеяла. Товар, пропавший из
каталога, уходит из раздела, но строка в базе остаётся: по его штрихкоду
могут собирать заказ, который уже в работе, — удалить её значило бы сломать
сборку. Вернули товар из архива — он снова виден.

Если Ozon ответил пустым списком, каталог не трогается: это похоже на сбой, а
не на опустевший склад, и отправлять всё в архив на таком основании нельзя.

**Набор** — то, ради чего раздел и появился. На Ozon набор это **обычный
товар**: один SKU, один артикул, один штрихкод, одна позиция в отправлении.
Площадка не знает, что на складе его собирают из нескольких разных вещей со
своими штрихкодами. А сборщик сканирует именно их — наклейки набора на полке
просто нет. Панель на такой скан отвечала «СТОП: товар не из этого
отправления»: SKU части в составе отправления не значится.

Состав задаётся здесь и живёт **только в панели** — площадке его не отправить,
да и незачем: собирают на складе. Часть набора это либо товар каталога (тогда у
неё есть название и фото), либо просто штрихкод с названием: не всё, что лежит
в наборе, продаётся отдельно — вкладыш, пакет, подарок из другой поставки.
У каждой части своё количество на один набор.

**Как это работает при сборке.** Скан части засчитывается в позицию набора, и
на экране сборщика под набором видно, что ещё взять с полки: «Чайник 1/1,
Наушники 1/2, Открытка 0/1». Набор закрывается, только когда набраны **все**
части — по одной части позицию закрыть нельзя, иначе в коробку уедет половина
комплекта. Лишняя часть даёт предупреждение, как и лишний скан обычного товара.
Если у набора есть своя наклейка, она по-прежнему работает: отсканировали её —
части не нужны.

В отчёт об отгрузке попадает **набор**, а не его содержимое: отгружен он.

Ограничения сознательные: набор не может состоять из самого себя, а вложенные
наборы запрещены — считались бы они молча неправильно, поэтому панель прямо
отказывает и просит перечислить части напрямую. Состав сохраняется целиком, а
не по частям: на экране видно ровно то, что уедет в базу.

### 8. Роли и доступ к разделам

Роль отвечает за то, что человеку можно делать **с самой панелью**; разделы —
какие **экраны** он видит. Это две разные вещи, и раньше они были одной:
администратор видел всё, сборщик три экрана, середины не существовало.

| Роль | Что может |
|---|---|
| **Владелец** | всё. Меняет пароли и права всем, включая других владельцев. Его разделы не урезаются. Только он переделывает принятое: снимает подтверждение акта и удаляет акт |
| **Администратор** | ведёт работу склада: заводит сотрудников, выдаёт доступы, правит ключи и настройки. **Владельца не трогает** — ни роль, ни разделы, ни пароль |
| **Сборщик** | работает на складе. Разделы выдаются галочками |

**Разделы выдаются галочками** в «Настройках» → «Сотрудники и доступы»: Сборка,
Заказы, Возвраты, Товары, Отчёты, Журнал, Настройки. Сборщику можно выдать
«Отчёты» — и он их откроет; администратора можно оставить без «Заказов» — и он
их не увидит. Снятая галочка закрывает экран сразу, без нового входа: разделы
читаются из базы на каждом запросе.

«Настройки» сборщику не выдать: там ключи площадок и выдача прав. Кому это
нужно — тот администратор, и роль у него должна быть честная.

**Почему администратор не дотягивается до владельца.** Иначе «администратор» и
«владелец» были бы одним и тем же: первый сменил бы владельцу пароль и вошёл
бы вторым. Поэтому владельца — его роль, разделы, пароль и включение — меняет
только владелец, и назначить владельцем тоже может только он.

**Последнего владельца не убрать**: ни понизить, ни отключить. Без владельца
некому менять пароли и права, и чинить панель пришлось бы руками в базе.

Ссылки в шапке рисуются по выданным разделам, но **адрес проверяется на
сервере** — спрятанная ссылка сама по себе ничего не закрывает.

При обновлении владельцем становится первый администратор — тот, кого завёл
установщик. На новой установке первая учётка создаётся сразу владельцем.

### 9. Журнал (`/logs`) и Настройки (`/settings`)

Журнал сканов и действий с фильтрами. В настройках администратор вводит **ключи
Seller API прямо в панели** — они проверяются на связь, сохраняются в базе и
применяются сразу, без правки `.env` и перезапуска службы. Там же — состояние
синхронизации и управление сотрудниками (роли «администратор» и «сборщик»).

## Быстрый старт

```bash
git clone https://github.com/kkkola000/ozon-pack.git && cd ozon-pack
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env
echo "ADMIN_PASSWORD=admin123" >> .env
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8080
```

Откройте `http://localhost:8080`, войдите как `admin` / `admin123` и добавьте
кабинет с ключами: **Настройки → Кабинеты**. До этого панель пуста — данные она
берёт только у площадок и ничего не придумывает.

## Развёртывание на VPS

Путь установки один: панель службой systemd, за nginx, со входом только из сети
VPN. Альтернативы (Docker, установка вручную, панель на открытом порту) убраны
намеренно — каждая была ещё одной дверью, которую можно открыть по
невнимательности, а найденная дыра выглядела ровно так.

Что нужно заранее: сервер Ubuntu/Debian, домен, направленный на него, и уже
поднятый туннель WireGuard. Сам VPN эти скрипты не ставят и не трогают — им
нужна только его подсеть.

### Одной командой

```bash
curl -fsSL https://raw.githubusercontent.com/kkkola000/ozon-pack/HEAD/deploy/setup.sh \
  | sudo bash -s -- --domain panel.example.com --email admin@example.com \
                    --vpn-subnet 10.8.0.0/24
```

Подставьте свою подсеть туннеля. Скрипт ставит панель и службу systemd,
поднимает nginx с сертификатом Let's Encrypt, закрывает прямой доступ к порту
и включает ограничение по VPN на обоих уровнях. В конце печатает адрес, логин
и пароль администратора — пароль показывается один раз.

Без домена — сертификат на IP-адрес сервера: `--ip` вместо `--domain`.

### По шагам

Если удобнее видеть каждый этап отдельно:

```bash
# 1. Панель и служба systemd
curl -fsSL https://raw.githubusercontent.com/kkkola000/ozon-pack/HEAD/deploy/install.sh -o install.sh
sudo bash install.sh --no-firewall

# 2. nginx и сертификат
sudo bash /opt/ozon-pack/deploy/ssl.sh --domain panel.example.com --email admin@example.com

# 3. Вход только из сети VPN
sudo bash /opt/ozon-pack/deploy/vpn-only.sh --subnet 10.8.0.0/24 --yes
```

Шаг 3 идёт после шага 2, а не до: `vpn-only.sh` дописывает правило в готовый
конфиг сайта, которого до `ssl.sh` ещё нет. Подсеть можно не указывать — тогда
скрипт возьмёт её с интерфейса `wg0` сам.

Полезные флаги `install.sh`: `--port N`, `--dir PATH`, `--user NAME`,
`--branch NAME`, `--no-service` (для контейнеров и WSL), `--yes`, `--help`.

### Проверка

```bash
sudo bash /opt/ozon-pack/deploy/vpn-only.sh --status
sudo ss -ltnp | grep :8080        # адрес должен быть только 127.0.0.1
```

С устройства **без** VPN `curl -sI https://panel.example.com` должен дать `403`.

Снять ограничение, если что-то пошло не так:

```bash
sudo bash /opt/ozon-pack/deploy/vpn-only.sh --off
```

### Обновление установленной панели

Обновляет тот же скрипт установки: он подтягивает свежий коммит, **пересобирает
юнит systemd**, дописывает в `.env` появившиеся настройки (заданные значения не
трогает) и перезапускает службу. База, журнал сборки и ключи остаются на месте.

```bash
curl -fsSL https://raw.githubusercontent.com/kkkola000/ozon-pack/HEAD/deploy/install.sh -o install.sh
sudo bash install.sh --yes
```

> **`git pull` + `systemctl restart` недостаточно при обновлении с версий до
> 1.9.** Раньше адрес, который слушает панель, был вписан прямо в юнит systemd,
> и без его пересборки панель продолжит слушать все интерфейсы — то есть
> останется доступной по `http://IP-сервера:8080` в обход nginx и VPN.
> Запускайте `install.sh`, а не перезапуск службы.

**Если перед панелью стоит nginx или включён доступ только по VPN**, после
обновления прогоните настройку доступа ещё раз — она заново закроет прямой
доступ и пропишет, чьему `X-Forwarded-For` верить:

```bash
sudo bash /opt/ozon-pack/deploy/ssl.sh --domain ВАШ-ДОМЕН --email ПОЧТА
# или, если ограничивали доступ сетью VPN:
sudo bash /opt/ozon-pack/deploy/vpn-only.sh --subnet ВАША-СЕТЬ
```

Если панель осталась от прежней установки в Docker, этот шаг обязателен: без
него она перестанет видеть настоящий адрес сотрудника и будет считать, что все
запросы приходят с адреса docker-моста. При заполненном `IP_ALLOWLIST` это
закроет вход всем. Ставить панель в Docker заново больше нечем — путь
установки один.

Проверить после обновления:

```bash
sudo ss -ltnp | grep :8080     # за nginx адрес должен быть только 127.0.0.1
curl -s localhost:8080/healthz # version должен показать новую версию
```

**Все сотрудники войдут заново.** Выданные раньше куки не содержат метки пароля,
по которой панель теперь узнаёт о его смене, поэтому после выкладки они
перестают действовать. Разовое неудобство, повторно это не потребуется.

### Полезные команды

```bash
systemctl status ozon-pack        # состояние службы
journalctl -u ozon-pack -f        # живой журнал
systemctl restart ozon-pack       # после правки .env
```

### HTTPS отдельно (если панель уже установлена)

```bash
sudo bash /opt/ozon-pack/deploy/ssl.sh --domain panel.example.com --email admin@example.com
```

Скрипт ставит nginx перед панелью, выпускает сертификат Let's Encrypt, включает
автопродление с перезагрузкой nginx, переводит панель на `127.0.0.1` (снаружи
она остаётся доступна только по https) и закрывает её прямой порт в ufw.

Три режима:

| Режим | Команда | Сертификат |
|---|---|---|
| Домен (рекомендуется) | `--domain panel.example.com` | Let's Encrypt, 90 дней, доверенный браузерами |
| Только IP, домена нет | `--ip` | Let's Encrypt на IP-адрес, 160 часов, продлевается автоматически |
| Закрытая сеть | `--self-signed` | Самоподписанный, браузер предупреждает |

Что нужно до запуска: A-запись домена ведёт на IP сервера (скрипт проверит и
скажет, если нет), порт 80 открыт — по нему Let's Encrypt проверяет владение.
Если домен проксируется через Cloudflare, на время выпуска отключите
проксирование («серое облако»).

Флаги: `--staging` (тестовый сервер LE, без лимитов), `--hsts` (браузеры
запомнят https на 180 дней), `--keep-open` (оставить прямой доступ по http),
`--help`.

Проверить, что продление работает: `sudo certbot renew --dry-run`.

Сертификаты на IP-адрес Let's Encrypt выдаёт с января 2026: они живут 160 часов
(чуть больше шести суток), поэтому автопродление обязательно — скрипт заводит
для него таймер systemd. Домен всё же удобнее: сертификат на 90 дней, адрес не
сломается при смене сервера, и сотрудникам проще запомнить.

### Доступ только через VPN (WireGuard)

Ограничение ставится на двух уровнях сразу, и это не перестраховка: правило
в nginx — одна точка отказа, конфиг сайта может потерять строку `include`,
и панель молча откроется всему интернету. Поэтому тот же список адресов
попадает в `IP_ALLOWLIST`, и панель сверяет адрес посетителя сама, не полагаясь
на прокси. Снаружи не видно даже формы входа — запрос получает 403 до того,
как дело дойдёт до пароля.

**Сразу при установке** — панель поднимется уже закрытой (слушает только
localhost, порт в файрвол не открывается, оба уровня настроены):

```bash
curl -fsSL https://raw.githubusercontent.com/kkkola000/ozon-pack/HEAD/deploy/setup.sh \
  | sudo bash -s -- --domain panel.example.com --email admin@example.com \
                    --vpn-subnet 10.8.0.0/24
```

**Если панель уже работает** — одной командой, WireGuard она не трогает:

```bash
sudo bash /opt/ozon-pack/deploy/vpn-only.sh
```

Скрипт сам находит сеть туннеля (`wg0`, обычно `10.8.0.0/24`) и просит nginx
отвечать только ей и самому серверу; всем остальным адресам — `403`. Ключи,
пароли и служба панели остаются как были.

```bash
sudo bash /opt/ozon-pack/deploy/vpn-only.sh --status   # что сейчас и кто заходил
sudo bash /opt/ozon-pack/deploy/vpn-only.sh --off      # открыть обратно
```

Сеть можно задать и вручную — например, если туннель поднят не через
`wg-quick` или сетей несколько:

```bash
sudo bash /opt/ozon-pack/deploy/vpn-only.sh --subnet 10.8.0.0/24
sudo bash /opt/ozon-pack/deploy/vpn-only.sh --subnet 10.8.0.0/24,10.9.0.0/24
sudo bash /opt/ozon-pack/deploy/vpn-only.sh --subnet 10.8.0.0/24 --allow 203.0.113.10
```

Указанная руками сеть заменяет найденную автоматически. Принимается и сеть
(`10.8.0.0/24`), и один адрес (`10.8.0.5`), и IPv6; адрес хоста приводится к его
сети — `10.8.0.1/24` станет `10.8.0.0/24`. Опечатку скрипт отсеет до того, как
тронет конфиг: правило не перезапишется. Свою сеть видно командой
`ip -o addr show wg0` или `sudo wg show`.

Остальные флаги: `--allow 203.0.113.10` (пустить ещё один адрес или сеть,
например офисный), `--yes` (без вопросов), `--help`.

Что важно знать:

* **SSH и сам WireGuard не затрагиваются** — запереть себя на сервере скрипт не
  может. Файрвол он тоже не трогает, только проверяет, что порт туннеля в ufw
  открыт, и предупреждает, если нет.
* **Сертификат продолжает продлеваться.** Адрес `/.well-known/acme-challenge/`
  остаётся открытым для всех, иначе Let's Encrypt не смог бы подтвердить домен.
* **Доступ по SSH — это доступ ко всему.** У кого есть вход на сервер, тот
  пробросит порт (`ssh -L 8080:127.0.0.1:8080`) и откроет панель мимо VPN.
  Так задумано: адрес `127.0.0.1` остаётся разрешённым всегда, каким бы ни был
  `IP_ALLOWLIST`. Через него работают проверка здоровья контейнера и скрипты
  развёртывания, и это же путь починить панель, если туннель отвалится.
* **Внутри туннеля ограничений нет.** Любое устройство из сети VPN дойдёт до
  формы входа, дальше его держит только пароль.
* **Списку адресов можно доверять, только пока верно `FORWARDED_ALLOW_IPS`.**
  Со значением `*` адрес посетителя подделывается заголовком `X-Forwarded-For`,
  и ограничение по подсети обходится. Панель предупреждает об этом в журнале
  при запуске.
* **Панель должна слушать только localhost.** Правило nginx закрывает порты 80
  и 443, но свой порт (`8080`) панель слушает сама: пока он смотрит наружу, в
  панель заходят по адресу сервера мимо VPN, мимо https и мимо журналов nginx.
  Скрипт это проверяет и закрывает сам: службе прописывает `HOST=127.0.0.1`
  (панели, оставшейся в Docker, — `BIND_ADDR=127.0.0.1`), после чего
  перезапускает её и
  **перечитывает, что слушает порт на самом деле**. Если порт всё ещё открыт,
  скрипт говорит об этом прямым текстом и завершается с ошибкой, а не рапортует
  «Готово»: проверить самому — `sudo ss -ltnp | grep :8080`, там должен быть
  только `127.0.0.1`.
* **Домен должен резолвиться в адрес туннеля** (или в адрес сервера, если у вас
  full-tunnel VPN) — иначе браузер просто не дойдёт до nginx.
* Правило лежит в `/etc/nginx/snippets/ozon-pack-access.conf`, а конфиг сайта
  только подключает его строкой `include`. Поэтому повторный запуск `ssl.sh`
  (например, при перевыпуске сертификата) ограничение не сбрасывает.

Если панель перестала открываться и через VPN — значит nginx видит не тот адрес,
с которого вы пришли. Посмотрите журнал и разрешите именно его:

```bash
sudo tail -5 /var/log/nginx/access.log
sudo bash /opt/ozon-pack/deploy/vpn-only.sh --allow ЭТОТ-АДРЕС
```

### Ключи площадок

Вносятся в самой панели: **Настройки → Кабинеты**. Панель проверяет связь,
сохраняет ключи и сразу переключает кабинет в боевой режим — перезапуск не нужен.

| Площадка | Где взять |
|---|---|
| Ozon | Личный кабинет → **Настройки → Seller API → Сгенерировать ключ**: `Client-Id` и `Api-Key` |
| Avito | Личный кабинет → **Настройки → Профиль → API**: `client_id` и `client_secret` |

Для первого кабинета Ozon ключи можно вместо этого прописать в `.env`
(`OZON_CLIENT_ID`, `OZON_API_KEY`) и перезапустить службу; ключи, введённые в
панели, имеют приоритет над файлом. Ключи Avito живут только в панели.
Без ключей кабинет ничего не загружает: списки остаются пустыми, а в шапке
горит «НЕТ КЛЮЧЕЙ». Придуманных данных панель не показывает никогда.

## Настройки (`.env`)

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `OZON_CLIENT_ID`, `OZON_API_KEY` | — | Ключи Seller API для первого кабинета. Можно не задавать и ввести их в «Настройках» панели |
| `AVITO_API_URL` | `https://api.avito.ru` | Адрес Avito API |
| `AVITO_DAYS_BACK` | `30` | За сколько дней назад запрашивать заказы Avito |
| `PORT` | `8080` | Порт панели |
| `HOST` | `127.0.0.1` | Адрес, который слушает панель. Снаружи к ней ходят только через nginx, поэтому по умолчанию — localhost. Менять значит открывать вторую дверь |
| `BIND_ADDR` | — | Только для панели, оставшейся от прежней установки в Docker: адрес публикации порта контейнера. `vpn-only.sh` выставляет его сам |
| `FORWARDED_ALLOW_IPS` | `127.0.0.1` | Чьему `X-Forwarded-For` верить, определяя адрес посетителя. Указывать адрес своего прокси, не `*`: со звёздочкой любой подделает свой IP и обойдёт `IP_ALLOWLIST` вместе с защитой от подбора пароля |
| `ADMIN_LOGIN` / `ADMIN_PASSWORD` | `admin` / генерируется | Первый администратор (создаётся один раз) |
| `IP_ALLOWLIST` | пусто | Доступ только с этих адресов/подсетей, через запятую |
| `SESSION_TTL_HOURS` | `24` | Срок жизни сессии |
| `SYNC_INTERVAL` | `60` | Как часто опрашивать Ozon по отправлениям, сек |
| `SYNC_RETURNS_INTERVAL` | `300` | То же для возвратов, сек |
| `SYNC_DAYS_BACK` / `SYNC_DAYS_FORWARD` | `30` / `30` | Окно выборки отправлений |
| `REQUIRE_ALL_ITEMS` | `1` | Требовать скан каждого товара перед закрытием |
| `AUTOPRINT` | `1` | Печатать стикер сразу при открытии отправления сканом товара. Открытое сканом самого стикера не печатается: он уже в руках |
| `AUTO_SHIP_ON_SCAN` | `0` | Собирать в Ozon прямо при скане (иначе — кнопкой в «Заказах») |
| `CLAIM_TTL_MINUTES` | `30` | На сколько отправление закрепляется за сборщиком |
| `TZ_OFFSET_HOURS` | `3` | Часовой пояс склада для отображения дат |
| `RETURNS_READY_STATUSES` | `ArrivedAtReturnPlace` | Статусы возвратов, которые панель загружает («В пункте выдачи»). Обычно удобнее менять в Настройках панели — там значение перекрывает файл |

После правки `.env` — `sudo systemctl restart ozon-pack`.

## Печать стикеров

На принтер уходит **файл, который отдал Ozon, без изменений** — панель его не
перерисовывает. Печатает браузер сборщика, серверу принтер не нужен.

* **Chrome, Edge, Windows** — стикер уходит на принтер сам, сразу после скана товара.
* **Safari на macOS** — файл открывается в отдельной вкладке: печатать PDF из
  скрытого окна Safari не умеет, выходит пустой лист. Вкладка одна на все стикеры,
  печать запускается автоматически, а если Safari её не даст — по ⌘P.

Рекомендации по принтеру: термопринтер по умолчанию, размер бумаги равен размеру
этикетки (обычно 75×120 мм), поля «нет», масштаб 100 %, колонтитулы отключены.
Один раз настроенные параметры браузер запоминает.

Если стикер на бумаге выглядит не так, как в личном кабинете Ozon, дело в
параметрах бумаги: панель печатает файл Ozon как есть. Сам файл можно открыть
кнопкой «Открыть PDF» у отправления.

## Методы Ozon Seller API

| Что | Метод |
|---|---|
| Список отправлений FBS | `POST /v3/posting/fbs/list` |
| Одно отправление | `POST /v3/posting/fbs/get` |
| Сборка (в «Ожидает отгрузки») | `POST /v4/posting/fbs/ship` |
| Стикер отправления | `POST /v2/posting/fbs/package-label` (при недоступности — `/v2/posting/fbs/package-label/create` + `/v1/posting/fbs/package-label/get`) |
| Отправление по штрихкоду | `POST /v2/posting/fbs/get-by-barcode` |
| Карточки товаров (штрихкоды) | `POST /v3/product/info/list` |
| Возвраты FBO и FBS | `POST /v1/returns/list` |
| Возвраты по пунктам выдачи | `POST /v1/returns/company/fbs/info` |
| Штрихкод на выдачу возвратов | `POST /v1/return/giveout/get-pdf` |

Ошибки Ozon не роняют панель: запросы повторяются с нарастающей паузой,
данные хранятся локально в SQLite, последняя ошибка синхронизации видна в «Настройках».

## Методы Avito API

| Что | Метод |
|---|---|
| Токен доступа (client_credentials, 24 ч) | `POST /token` |
| Проверка ключей | `GET /core/v1/accounts/self` |
| Список заказов (в том числе возвраты) | `GET /order-management/1/orders` |
| Подтвердить / отправить заказ | `POST /order-management/1/order/applyTransition` |
| Задача на генерацию этикеток | `POST /order-management/1/orders/labels` |
| Скачать этикетку (PDF) | `GET /order-management/1/orders/labels/{taskID}/download` |

Токен кэшируется на сутки и перезапрашивается сам, если Avito ответил `401`.
Заказы запрашиваются только в статусах `on_confirmation`, `ready_to_ship` и
`on_return` — остальные в панель не попадают. Отдельного метода для возвратов
у Avito нет: состояние возврата приходит в самом заказе, в поле `returnPolicy`.
Фильтровать возвраты по `returnStatus` на стороне API нельзя, поэтому лишнее
отбрасывается уже в панели — сохраняются только `ready_to_pickup`.

Возвраты запрашиваются **отдельным запросом и без `dateFrom`**. Этот параметр
отсекает заказы по дате их создания, а не по дате возврата: покупку сделали два
месяца назад, вернули сегодня — с окном `AVITO_DAYS_BACK` такой возврат в
панель бы не попал. Отдельный запрос заодно не даёт возвратам конкурировать с
текущими заказами за страницы выдачи.

## Безопасность

Сразу после установки панель работает **по HTTP — трафик не шифруется**, включая
пароли сотрудников. Что стоит сделать:

* включить HTTPS — `deploy/ssl.sh` (см. выше), это бесплатно и занимает минуту;
* закрыть панель снаружи — `deploy/vpn-only.sh`, если у вас есть WireGuard;
* задать `IP_ALLOWLIST` (адреса склада) или закрыть порт файрволом;
* задать длинный `ADMIN_PASSWORD` и завести каждому сборщику свой логин —
  журнал ценен, только если по нему видно конкретного человека.

За nginx панель продолжает видеть настоящий IP сотрудника (`X-Forwarded-For`),
поэтому белый список адресов и ограничение попыток входа работают как прежде,
а кука сессии автоматически помечается `Secure`. Заголовку верят только адреса
из `FORWARDED_ALLOW_IPS` — иначе IP подделал бы кто угодно вместе с обходом
белого списка.

Встроено: пароли — PBKDF2-SHA256 (240 000 итераций), подписанные HttpOnly-сессии,
CSRF-токен на изменяющих запросах, ограничение попыток входа (10 за 5 минут),
права `0600` на файл базы.

**Смена пароля закрывает прежние входы.** Если сборщик уволился или его пароль
мог утечь, смените пароль в «Настройках» — все его открытые вкладки попросят
войти заново, ждать окончания `SESSION_TTL_HOURS` не нужно. Отключение
сотрудника (галочка «включён») действует так же сразу.

## Обслуживание

```bash
# Резервная копия (вся история сборки — в одном файле)
sqlite3 data/ozon-pack.db ".backup '/backup/ozon-pack-$(date +%F).db'"

# Обновление (см. раздел «Обновление установленной панели»)
sudo bash install.sh --yes                   # пересоберёт юнит и перезапустит службу

# Тесты (нужны пакеты для разработки — на сервер они не ставятся)
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest
```

Данные лежат в `data/`: база SQLite и ключ подписи сессий. Каталог переживает
пересборку контейнера, его и нужно бэкапить.

**Бэкапить нужно весь каталог `data/`, а не только базу.** Ключи площадок
(Api-Key Ozon, client_secret Avito) хранятся в базе зашифрованными, а ключ
шифрования лежит в `data/.secret_key` (или задан через `SECRET_KEY` в `.env`).
База без этого секрета бесполезна — восстановив только её, ключи придётся
вводить заново в «Настройках». Обратная сторона: копия базы сама по себе ключи
не выдаёт, поэтому `data/.secret_key` стоит хранить отдельно от бэкапа базы.

## Ограничения

* Отправление собирается одной коробкой. Многоместные отправления помечаются
  меткой в интерфейсе, но разбивку по коробкам нужно делать в личном кабинете Ozon.
* Коды маркировки «Честный знак» не передаются в Ozon — панель только подсвечивает,
  что отправление их требует.
