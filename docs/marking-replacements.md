# Честный знак: замена и проверка

На каждую физическую единицу товара приходится один текущий код. Сохранение
скана резервирует GTIN и серийный номер во всех кабинетах и площадках панели.
Резерв нужен и во время передачи: другой сборщик не сможет одновременно
назначить эту марку другому заказу. HTTP 200 не означает принятия марки.

## Подтверждённая замена

После явного отказа площадки сборщик может заменить код. Прежняя запись
становится неактивной. Её резерв освобождается только после того, как:

1. Новый код для той же единицы принят площадкой и заказ подтверждён готовым.
2. Получен полный свежий состав экземпляров именно этого заказа.
3. Подтверждено наличие полных текущих кодов и успешная проверка каждого.
4. Прежнего GTIN и серийного номера нет среди маркировок всего заказа.

Для Ozon используются `exemplar/create-or-get` v6 и `exemplar/status` v5.
Идентификаторы экземпляров и состав сверяются с сохранённым заказом.
Для Яндекса проверяются полный заказ с `cisFull` и индивидуальные результаты
`identifiers/status`. Короткий `cis` не доказывает отсутствие полного кода.

Освобождение резерва, запись истории и события журнала выполняются в одной
транзакции под блокировкой заказа с повторной проверкой ревизий. Текущий код
и статус принятого заказа сохраняются. Старый код виден в «Стикеры → Честный
знак» как «Отвязан»; причина в истории — `replaced`.

Таймаут, HTTP 403, неполный состав, изменившиеся экземпляры, незавершённая
проверка или сценарий Яндекса «Не записан ЧЗ на маркете» не освобождают резерв.
Сама сверка замен не меняет данные на площадке.

## Накопленные привязки

После обновления фоновый обработчик проверяет старые неактивные записи
`error` и `removed`, если для той же единицы есть принятый текущий код и заказ
имеет локальный статус `accepted`. За проход выбирается до пяти заказов.
Незавершённая сверка повторяется не чаще раза в пять минут на заказ.
При конфликтующем скане в другом заказе также выполняется сверка владельца.

Если API больше не позволяет доказать состав старого заказа или экземпляры
нельзя однозначно сопоставить, резерв сохраняется. Удалять строки реестра
вручную не требуется: явное состояние `released` переживает перезапуск и
заполнение реестра из старых данных.

## Статусы Яндекс Маркета

Панель сохраняет `CisStatusType` и `CisSubstatusType` отдельно от внутреннего
состояния передачи. Их описания показываются в существующем сообщении
сканера, подсказке «М» и карточке марки в архиве.

| Статус | Поведение |
|---|---|
| `OK` | Зелёная «М» после сверки полного кода и подтверждения готовности |
| `INVALID` | Красная «М», завершение блокируется; показывается только описание `CisSubstatusType` |
| `IN_PROGRESS` | Серая «М», ожидание проверки |
| `NOT_ON_VALIDATION` | Серая «М», код не отправлен на проверку |
| `FAILED` | Серая «М»; повтор передачи разрешён только пока заказ `STARTED` |

Все 16 документированных причин `INVALID` переводятся фиксированными
описаниями из инструкции. Для отсутствующей или неизвестной причины
используется общее описание `INVALID`. У других статусов `substatus`
игнорируется. Внешние тексты ошибок, коды и ключи API не подставляются
в описание причины.

Схема существующей SQLite-базы расширяется автоматически при запуске;
заказы, коды и привязки сохраняются.

## Повторный скан и отмена сборки

Отмена сборки освобождает рабочее место сборщика, но сохраняет полный ЧЗ,
его привязку и результат передачи. Повторный скан неподтверждённого кода
возобновляет проверку и очередь, не создавая вторую запись и дубликат печати.
Сообщение о локальном сохранении не означает, что код принят площадкой.

Для Яндекса повторная передача по явному скану допускается в `STARTED`, если
предыдущая запись получила определённый ответ, свежие данные не содержат
конфликтующих кодов, а метод проверки вернул пустой список CIS или
`NOT_ON_VALIDATION`. `IN_PROGRESS`, недостаточные права, неполный ответ и
неизвестный результат предыдущей записи не разрешают такую повторную запись.
`FAILED` обрабатывается по прежним правилам повторной проверки.

В «Стикерах» по умолчанию видны сохранённые PDF и заказы с ЧЗ, даже если PDF
ещё не получен. У таких заказов остаётся состояние «Ожидает загрузки» и
работает кнопка «Честный знак»; скачивание PDF появится после его получения.

При отмене незавершённой сборки её строки отчёта получают статус «Сборка
отменена» и исключаются из количества отгруженных товаров и заказов. Ошибки
сборщика и журнал сохраняются. Повторная сборка учитывает ту же единицу один
раз с актуальным сборщиком и датой. Старые неверные отметки восстанавливаются
при запуске по событиям отмены; подтверждённое завершение защищает отчёт от
такой правки.

## Автопечать и диагностика

Первый скан ШК товара запускает одинаковую очередь печати у Ozon и Яндекса.
Если площадка ещё ждёт ЧЗ или подтверждение раскладки, очередь сохраняет
задание и заранее открытое браузерное окно до готовности стикера. Опросы не
дублируют печать, отмена сборки снимает неотправленное задание. Скан уже
имеющегося стикера не запускает повторную печать.

Результат проверки Яндекса запрашивается независимо от наличия `cisFull`:
отказ не должен оставаться невидимым только потому, что экземпляры ещё не
появились в заказе. Успешное завершение по-прежнему требует полного
сохранённого кода и `OK` для него.

Полный код может быть возвращён в `items[].instances[].cisFull` либо в
`delivery.boxesLayout[].items[].instances[].cis`. Во втором случае проверяются
полный состав коробок, количество и соответствие каждой физической единице.
Короткого CIS, неполной раскладки или противоречащих друг другу данных
недостаточно. Код одного товара в нескольких коробках учитывается один раз.
Перед освобождением старой привязки проверяются оба источника: старый ЧЗ,
оставшийся в коробках, продолжает удерживать свой резерв.

Команда на сервере читает существующий кабинет, заказ и ответ проверки,
не отправляя коды и не меняя статус заказа:

```sh
cd /opt/ozon-pack
sudo -u ozon .venv/bin/python -m app.order_requirements_diagnostics --market yandex --order НОМЕР_ЗАКАЗА
```

При нескольких кабинетах можно добавить `--account-id ID`. В выводе:

- `local`: состояние очереди, число попыток, время проверки и запрос повторного скана;
- `readback`: наличие полного сохранённого кода по каждой единице;
- `products[].layout_full_code_count`: сколько полных кодов вернулось в раскладке коробок;
- `identifiers_status`: статусы и причины проверки, совпадение с локальными единицами;
- `identifiers_status.error.http_status`: отказ доступа или другая ошибка запроса.

Значения ЧЗ, ГТД, ключи и сведения о покупателе в вывод не включаются.

Официальные схемы Яндекса: [CisDTO](https://github.com/yandex-market/yandex-market-partner-api/blob/main/openapi/components/schemas/CisDTO.yaml),
[CisStatusType](https://github.com/yandex-market/yandex-market-partner-api/blob/main/openapi/components/schemas/CisStatusType.yaml),
[CisSubstatusType](https://github.com/yandex-market/yandex-market-partner-api/blob/main/openapi/components/schemas/CisSubstatusType.yaml).
