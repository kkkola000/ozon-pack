# ЧЗ и дополнительные сведения: проверка Ozon и Яндекс Маркета

Дата сверки: 14 ноября 2026. Версия реализации: 1.68.3.
Область: заказы «Ожидают сборки» и «Ожидают отгрузки».

## Вывод

API различает три разных понятия: товар допускает маркировку,
маркировку обязательно передать сейчас, и код уже передан и принят площадкой.
ГТД, РНПТ и УИН — отдельные типы дополнительных сведений.
Отсутствие экземпляров в ответе само по себе не доказывает, что ЧЗ не требуется.

Версия 1.67.2 на сервере подтверждена пользователем. При этом реальные ответы
API отправления 51121561-0339-2 и SKU 6346622543 в этой облачной среде недоступны:
здесь нет производственных ключей кабинета. Скриншот показывает состояние
интерфейса, но не значения полей API. Точная причина для этого отправления
требует фактического ответа, а не очередного предположения о флагах.

## Ozon

Метод `/v3/posting/fbs/get` возвращает `requirements`: списки SKU, которым
нужно передать сведения для следующего статуса:

- `products_requiring_mandatory_mark` — ЧЗ;
- `products_requiring_gtd` — ГТД;
- `products_requiring_rnpt` — РНПТ;
- отдельные списки для веса, IMEI, УИН и страны.

Поле `products[].mandatory_mark` помечено в схеме как устаревшее. Поле
`available_actions` перечисляет доступные действия, включая
`ship_with_additional_info` и `update_cis`. Оно не является перечнем
маркируемых SKU. В описании нет гарантии, что у каждого товара с доступным
ЧЗ в обоих статусах обязательно будет одно из этих действий.

Метод `/v6/fbs/posting/product/exemplar/create-or-get` содержит сведения
по продуктам и экземплярам:

| Поле продукта | Смысл по схеме |
| --- | --- |
| `is_mandatory_mark_needed` | Необходимо передать ЧЗ |
| `is_mandatory_mark_possible` | Возможно заполнить ЧЗ |
| `is_gtd_needed` | Необходимо передать ГТД |
| `is_rnpt_needed` | Необходимо передать РНПТ |
| `is_jw_uin_needed`, `has_imei`, `is_weight_needed` | Другие данные экземпляра |

Данные экземпляров находятся в `exemplars[]`: `marks`, `gtd`,
`is_gtd_absent`, `rnpt`, `is_rnpt_absent`, `weight`. Наличие кода и необходимость
передать код — разные сведения. В определении `ExemplarMark.mark_type`
перечислены `mandatory_mark`, `jw_uin`, `imei`.

Для уже собранного отправления применяется последовательность:
`/v6/fbs/posting/product/exemplar/set` → проверка
`/v5/fbs/posting/product/exemplar/status` →
`/v1/fbs/posting/product/exemplar/update` для сохранения обновлённых данных
в статусе «Ожидает отгрузки». HTTP 200 метода set означает создание задачи.
Считывать требования и имеющиеся данные нужно в обоих рабочих статусах:
`awaiting_packaging` и `awaiting_deliver`.

**ГТД Ozon, уточнение для 1.70.8.** Сборщик может передать номер (`gtd` и
`is_gtd_absent: false`) либо выбрать «Не указывать» (`is_gtd_absent: true`,
без поля `gtd`). Выбор относится к отдельному экземпляру и не отменяет проверку
ЧЗ. Полный набор экземпляров передаётся вместе с сохранёнными маркировками;
при предварительной валидации поле `gtd` для такого экземпляра опускается,
поскольку метод validate не принимает `is_gtd_absent`.
Подтверждение требует однозначного ответа по всем экземплярам и фактического
номера или признака отсутствия в отправлении. Сбой проверки ГТД сам по себе
не является основанием заново отправлять уже сохранённые коды ЧЗ.

**Уточнение для 1.70.9.** Если в полном наборе экземпляров нет ни одного кода
в `marks`, предварительный `/validate` не вызывается. Выбор ГТД отправляется
через `/set`, который поддерживает `is_gtd_absent`; подтверждение через `/status`
и чтение фактических данных остаётся обязательным. При наличии маркировок
предварительная проверка выполняется до записи. Диагностика Ozon также сравнивает
идентификаторы экземпляров с локальным снимком и показывает, была ли отправлена
текущая ревизия, чтобы отличать отказ до записи от отказа самой записи.

Прямой сайт docs.ozon.ru при проверке возвращал цикл перенаправлений.
Поля сверены по опубликованной копии схемы Seller API:
[схема](https://github.com/vispar-tech/ozon-seller-api-schema/blob/main/schemas/ozon-seller-api-openapi.json).
Оригинальные ссылки:
[create-or-get](https://docs.ozon.ru/api/seller/#operation/PostingAPI_FbsPostingProductExemplarCreateOrGetV6),
[update](https://docs.ozon.ru/api/seller/#operation/PostingAPI_FbsPostingProductExemplarUpdateV1).

## Яндекс Маркет

Официальная схема `POST /v1/businesses/{businessId}/orders` возвращает
`items[].requiredInstanceTypes`:

| Значение | Смысл |
| --- | --- |
| `CIS` | ЧЗ обязателен |
| `CIS_OPTIONAL` | ЧЗ необязателен |
| `GTD` | ГТД |
| `RNPT` | РНПТ |
| `UIN` | УИН ювелирного изделия |

Переданные сведения находятся в `items[].instances[]`: `cis`, `cisFull`,
`gtd`, `rnpt`, `uin`. `cisFull` содержит криптохвост. Если магазин ещё не
передавал коды, `instances` может отсутствовать: по этому отсутствию нельзя
делать вывод, что товар не требует сведений.

Нужные стадии: `status=PROCESSING` с `substatus=STARTED` и `READY_TO_SHIP`.
Чтение заказа доступно по его ID для обеих стадий.

Для FBS/Экспресс передача кодов выполняется через
`PUT /v2/campaigns/{campaignId}/orders/{orderId}/boxes`, проверка —
`POST /v2/campaigns/{campaignId}/orders/{orderId}/identifiers/status`.
Изменять переданную раскладку схема разрешает до `READY_TO_SHIP`.
Метод `/identifiers` предназначен для DBS; его нельзя считать обходом
ограничения FBS. Нельзя приравнивать распознанный тип товара к разрешению
на запись кодов в любом статусе.

Источники из официального репозитория Яндекс Маркета:

- [BusinessOrderItemDTO](https://github.com/yandex-market/yandex-market-partner-api/blob/main/openapi/components/schemas/BusinessOrderItemDTO.yaml)
- [OrderItemInstanceType](https://github.com/yandex-market/yandex-market-partner-api/blob/main/openapi/components/schemas/OrderItemInstanceType.yaml)
- [OrderItemInstanceDTO](https://github.com/yandex-market/yandex-market-partner-api/blob/main/openapi/components/schemas/OrderItemInstanceDTO.yaml)
- [setOrderBoxLayout](https://github.com/yandex-market/yandex-market-partner-api/blob/main/openapi/paths/v2_campaigns_campaignId_orders_orderId_boxes.yaml)
- [provideOrderItemIdentifiers](https://github.com/yandex-market/yandex-market-partner-api/blob/main/openapi/paths/v2_campaigns_campaignId_orders_orderId_identifiers.yaml)

## Сборка в 1.68.3

ЧЗ и дополнительные сведения обрабатываются раздельно. «М» показывает
результат проверки ЧЗ: серый — ожидается скан/проверка, красный — отказ,
зелёный — подтверждение. ГТД вводится в поле **«Указать ГТД» под товаром**.
Для нескольких экземпляров доступны отдельные поля. По требованиям площадки
там же запрашиваются РНПТ, IMEI и вес (последние два — Ozon).
УИН ювелирных изделий в панели не используется: его флаги и старые требования
игнорируются, поле ввода не показывается. Ранее сохранённые зашифрованные значения
остаются в истории, но не участвуют во вводе, новых передачах и проверке ЧЗ.
В версии 1.68.3 ГТД не заменялась признаком «отсутствует» и не требовала сканирования ЧЗ.
Текущее поведение Ozon описано выше, в уточнении для 1.70.8.

По правилу владельца панели доступная маркировка (`is_mandatory_mark_possible`,
`CIS_OPTIONAL`) также обязательна в сборке. Это правило панели; оно не меняет
значение флагов в API.

При сканировании товара или стикера, открывающем сборку, Ozon всегда запрашивает
`/v6/fbs/posting/product/exemplar/create-or-get` для этого отправления.
Предварительные `requirements`/`available_actions` не являются условием запроса:
без них экземпляры всё равно проверяются. Готовый заказ читается так же, но
повторно в сборку через ship не отправляется. Яндекс использует
`items[].requiredInstanceTypes` из свежего ответа заказа.
В ранее открытом окне требования обновляются перед очередным сканом товара
или стикера; скан ЧЗ также использует свежие сведения. Это относится и к
окнам, оставшимся открытыми после обновления панели.
Запросы атрибутов, описания категории и offer-mappings для определения ЧЗ
при сборке не выполняются: права чтения каталога не нужны для этого шага.

Обычный товар без дополнительных требований после успешной проверки собирается
как прежде. Ошибка или неполный ответ метода требований не означает «ЧЗ не нужен»:
открытие/завершение блокируется до получения достоверных сведений. При отказе
Ozon сообщение отдельно указывает `create-or-get` и HTTP-статус без тела ответа.
Ранее подтверждённые требования и привязанные ЧЗ сохраняются, даже если площадка
убрала флаг после принятия данных. Сохранённое требование ГТД также не теряется.

Введённые данные сохраняются зашифрованными и привязываются к товару и его
единице. В Ozon запрос set содержит **полный набор продуктов и экземпляров**:
отдельный ввод ГТД сохраняет ЧЗ, а новый ЧЗ сохраняет ГТД, РНПТ и прочие
имеющиеся на площадке сведения. Для ЧЗ используется `mark_type=mandatory_mark`,
для IMEI — `imei`. Встроенная JSON-сериализация сохраняет GS как
`\u001d`, без двойного экранирования. В Яндекс передаётся полная раскладка
коробок с `instances` каждой физической единицы, включая дополнительные поля.

Передача начинается после сбора всех обязательных полей и ЧЗ заказа. HTTP 200
не разрешает завершение: нужны результаты проверки и подтверждение значений
чтением заказа. Ozon использует validate → set → status, затем ship (для нового
заказа) либо update (для готового) и повторное чтение. Для Маркета нужны точное
сохранение instances, результат проверки CIS и подтверждённый READY_TO_SHIP.
Ошибка ГТД отображается у поля и не превращается в отказ уже принятого ЧЗ.
Таймаут записи оставляет задачу на сверку, без слепого повторного запроса.
Скан стикера и завершение без скана подчиняются той же проверке.

Для готового FBS/Экспресс заказа Маркета новые сведения через boxes не
отправляются вопреки ограничению API: если точных данных ещё нет в заказе,
панель блокирует завершение и предлагает исправить заказ в кабинете площадки.
У Ozon требование изменить страну происхождения также показывается явной
ошибкой с необходимостью исправления в кабинете; ввод страны в сборке не добавлен.

При разделении Ozon сведения переходят в дочерние отправления по подтверждённым
идентификаторам экземпляров или точному ЧЗ. Если привязка не доказана, завершение
блокируется. На Маркете у одного товара в двух грузоместах остаётся одна запись
ЧЗ; в каждую часть раскладки передаются те же сведения единицы.

## Короткий ЧЗ и ввод GS

Поддерживаются коды с настоящими разделителями GS и короткий 37-символьный
профиль `01 + GTIN(14) + 21 + серия(13) + 93 + проверка(4)` без GS.
В коротком профиле поля определяются строго по длине и позиции. Произвольные
строки не делятся по первому вхождению `93`; неполный или неизвестный формат
возвращает ошибку без утверждения, что сканер настроен неверно.

Исходная строка после удаления служебного префикса символики/терминатора
сохраняется зашифрованной и передаётся площадке без вставки GS и без изменения
кавычек, регистра, серии или крипточасти. Дубликат обязан декодироваться в те же
байты: контроль выполняется при генерации, а тест также считывает изображение
из окончательного PDF. Для короткого профиля энкодеру не передаются отдельные
AI 21/93, поскольку такое представление добавило бы GS и изменило данные.

При сравнении ответа площадки поддерживаются два представления короткого ЧЗ:
с GS и без него. Совпадать должны все поля, включая полную крипточасть.
Сокращённый CIS не заменяет подтверждение полного кода. Сравнение не переписывает
исходную строку в архиве, API-запросе или дубликате; повторный скан эквивалентного
представления не создаёт второй код и не запускает повторную автопечать.

В поле сканирования принимается GS (ASCII 29), переданный клавиатурным сканером
как `Ctrl+]`, включая тот же физический `BracketRight` в другой раскладке.
AltGr/обычные символы и поля ГТД этим обработчиком не меняются. Текстовая запись
`\u001d` не считается настоящим GS и не преобразуется автоматически.

## Удаление маркировки в Ozon

При отмене сборки, повторном открытии и следующих сканах панель сверяет ранее
принятые коды с полным ответом create-or-get. Если принятый код исчез из своего
товара, а состав экземпляров подтверждён, активная привязка снимается. Код больше
не отображается в списке «Стикеры → Честный знак», а прежняя ссылка печати
недоступна до нового сканирования. Сам стикер отправления и его PDF сохраняются.
История снятия фиксируется в журнале без полного кода маркировки.

Серая «М» и блокировка завершения возвращаются для отсутствующей маркировки.
Повторно отсканировать тот же код для той же единицы заказа разрешено; он
проходит новую передачу/проверку и снова участвует в автопечати по настройке.
Остальные принятые коды заказа и введённая ГТД сохраняются. У уже разделённого
заказа повторная передача относится к текущему отправлению; завершённое
распределение по дочерним отправлениям повторно не запускается.

Отсутствие ещё не принятого кода в асинхронном процессе не считается удалением.
Во время checking/uncertain привязки не снимаются на основании пустых экземпляров.
Отмена сборки остаётся доступна при ошибке API, но сопровождается предупреждением
о незавершённой сверке. Если у каждого товара одна единица, новые ID экземпляров не мешают сверке по
товару. Изменившиеся ID/порядок нескольких одинаковых единиц требуют отдельной
сверки; привязки в такой ситуации не удаляются по предположению. Изменение
названия типа маркировки в API само по себе не считается удалением полного кода.
Перед новой записью queued-задача перечитывает требования: принятый ранее, а затем
удалённый с площадки код не восстанавливается автоматически вместе с записью ГТД.

В интерфейсе используется название **«Честный знак»**: кнопка архива, настройки
дубликата, общий принтер, подсказки сканирования и сообщения. Индикатор «М»
и внутренние идентификаторы маршрутов/настроек сохраняются.

## Диагностика реального заказа

Диагностический модуль запрашивает фактические сведения по конкретному заказу. Он не вызывает ship, set, update,
изменение коробок или статуса. Для Ozon вызывается create-or-get, который
предназначен для получения/создания идентификаторов экземпляров.

Запуск на сервере из каталога панели:

```bash
cd /opt/ozon-pack
sudo -u ozon .venv/bin/python -m app.order_requirements_diagnostics --market ozon --order 51121561-0339-2
```

Для Яндекса:

```bash
sudo -u ozon .venv/bin/python -m app.order_requirements_diagnostics --market yandex --order НОМЕР_ЗАКАЗА
```

При нескольких подходящих кабинетах укажите `--account-id ЧИСЛО`.
Используются уже настроенные ключи панели. В JSON выводятся версия,
статус, требуемые типы, флаги по SKU и количество имеющихся данных.
Пароли, ключи, полные ЧЗ, номера ГТД, адреса и данные покупателя не выводятся.
Ошибки API представлены классом ошибки и HTTP-статусом без тела ответа.
Перезапуск службы для запуска этого диагностического модуля не требуется.
